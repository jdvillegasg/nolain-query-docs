    The system philosophy

    This chapter explains the product bet, why responsibilities are split across four layers, and which invariants and trade-offs follow. The next chapter names the components; the workflow chapter owns the request-by-request journey.

    You do not need to know the codebase. By the end you will have a small vocabulary — sketch, artifact, Capability, Plan, intent — and a picture of four layers that everything else hangs on.

    The core bet

    Imagine a spreadsheet of invoices on your laptop. You want to ask “What is total revenue by country?” You do not want to upload the file to someone else’s warehouse. You also do not want a chatbot that invents a number.

    nolainquery’s bet is: local computation, remote reasoning.

    Your machine keeps the file, derives a compact description of it, runs whatever analysis comes back, and shows the result. The remote service does not receive the full dataset. It sees a sketch — column names, types, summaries, and, on clients that include them, a bounded set of sample rows or values — plus your question. It returns artifacts: executable analysis, and if you asked for them, a computation graph and a chart contract. Your machine runs those artifacts against the real file.

    The analogy is a librarian and a reading room. You do not ship the books to a consultant. You send the card catalog. The consultant writes a procedure (“pull these shelves, add these columns, rank the result”). You run the procedure in the room that actually has the books. The answer is true because it was computed there, not because the consultant asserted it.

    That split is the product. Everything below is how the split is kept reliable, cheap enough, and hard to misuse.

    Four layers

    Think of four floors, from closest to you (and to the file) to farthest from the data.

    Local layer          owns the file, derives the sketch, runs artifacts, shows results
Dialogue layer       decides whether this turn should generate anything
Synthesis layer      once admitted, produces typed artifacts
Settlement layer     who is calling, which model, what the reasoning costs

    The data plane is the local layer: own the file, compute, report. The control plane is dialogue + synthesis + settlement: reason, admit, charge. The sketch is the only interface between them. If a change requires the control plane to see more of the file, it is fighting this design.

    Local layer

    The local layer owns the file, derives the sketch, executes artifacts, and shows results. It is the only layer that may touch the complete dataset and the only one whose output counts as an answer grounded in real rows.

    It does not invent analysis, call models, or decide product scope. This makes privacy structural, while accepting that a thin sketch can hide file-specific quirks from remote reasoning.

    Dialogue layer

    The dialogue layer treats each user message as a conversation decision, not an automatic generation request. It can answer from the sketch, explain a prior result, refuse unsupported work, ask for clarification, or admit generation.

    It does not select pipelines or optional artifacts. The gate saves unnecessary generation and keeps product scope explicit, but adds model calls and can make the conversation unavailable when classification fails.

    Synthesis layer

    Once generation is admitted, the synthesis layer produces typed artifacts under a registered Capability, through a Plan. Three terms carry this model through the rest of the book:

    • A Capability is a product on the menu. Today: “descriptive analysis of one file.”
    • A Plan is a kitchen line for that product. Today: the Pandas line. Another line (Ibis) is catalogued and refused until it is implemented.
    • A Stage is a station on that line. Stations consume and produce artifacts. Optional artifacts (graph, chart) are request options on a Plan, not extra menu items.

    Policy constructs the pipeline; the model fills artifacts rather than designing the production line. This keeps optional outputs composable, though derived graph and chart artifacts can still drift from the executable code.

    Settlement layer

    The settlement layer identifies the caller, exposes the model catalog, and charges for remote reasoning as model calls complete. It does not execute data or decide which questions are in scope.

    Charging by call follows actual provider cost, so two apparently similar questions can cost different amounts when models, optional artifacts, or failure paths differ.

    Durable invariants

    The implementation can evolve without changing the product’s identity only while these boundaries remain true.

    Data stays local

    • The complete file stays on the user’s machine.
    • The cloud receives only the question and a sketch. Because sketches may contain bounded sample values, this is data minimization rather than a claim that no row values ever leave the machine.
    • Cloud artifacts are proposals. The answer becomes grounded only when the local layer executes them against the real file.

    Policy remains authoritative

    • Models may classify, interpret, and propose; registered policy decides what can run.
    • Conversation intent is not a generation Capability. A message can be useful without creating analysis.
    • Optional graphs and chart contracts are outputs of a Plan, not new products invented by a prompt.
    • A normal conversation turn must pass classification. If that machinery fails, the request stops with HTTP 503 instead of failing open into generation.

    Generated work remains bounded

    • Executable analysis is primary; graph and chart artifacts are derived.
    • Static checks precede delivery, but execution against the full dataset remains local.
    • Repair is feedback about execution, not permission to reinterpret the question or switch products.
    • Retries and cancellation are bounded. Their exact budgets and stage behavior belong in The parts of the system.

    Cost follows remote reasoning

    • Each completed model call is charged as reasoning work; queueing and local execution are not cloud charges.
    • Work already completed remains chargeable even if a later stage fails or the caller cancels.
    • A caller without spending authority does not enter paid reasoning work.

    Strengths, assumptions, tradeoffs

    Strengths. Structural privacy. Answers grounded in execution. A conversation that can refuse. A small, explicit product surface. Deterministic belts around generative steps. Cost aligned with work.

    Assumptions. The sketch is representative enough, often enough. A single executable-analysis engine is a sufficient lingua franca between control plane and data plane. The desktop is a trusted partner: it executes, it reports, it owns optional-artifact toggles. Bounded retries and a required classifier gate are preferable to unclassified generation. Users will accept paying for the gate and for failed steps because those were real model calls.

    Choice What it buys What it costs
    Sketch only, never the file Privacy, simpler trust, local truth Missed quirks; generation can be locally wrong
    Intent gate before generation Cheap refusals; clearer product boundary Extra calls; classifier failure makes the turn unavailable
    Classifier suggests, policy admits The model cannot invent pipelines Catalog and policy must stay the real source of truth
    Optional artifacts, not extra Plans One Plan, many outputs Options must be carried on every turn
    Analysis first, graph and chart derived Fast path to something executable Drift between code, graph, and spec
    Repair without re-classifying Fast correction on exec errors Repair cannot change the question’s meaning
    Charge every model call immediately Matches vendor cost Users pay for failed steps and for the gate itself
    Short-lived session memory Simple operations History is not a durable account object
    Single enabled Capability Honest “out of scope” Dialogue must keep saying no
    Direct generation beside conversation Same artifacts without a chat Two paths that can drift if they are not kept honest

    Room for improvement

    The current shape is a working compromise, not a finished architecture.

    The sketch is still a sketch. Better summaries, better samples, and honest signals about data quality would raise hit rate without moving the file.

    One Capability is both a strength and a ceiling. “Out of scope” is doing a lot of work. A second product will test whether intent, policy, and artifacts actually compose.

    A second engine is a promise. Until another Plan is implemented, “Plan = engine” is vocabulary, not a proven split.

    Code, graph, and chart can disagree. Treating the graph as a projection is convenient. Making it the executable source of truth would make the canvas trustworthy. That is not done.

    Dialogue is a good gate and a weak memory. Sessions expire, ownership is bound to the API key that created them, and follow-up quality depends on whatever was last stored.

    Wording-based safety duplicates part of the catalog boundary. Classifier failure already stops the turn. Out-of-scope behavior can become more uniform when the Capability catalog replaces the remaining phrase lists.

    Settlement is call-shaped; the product is still question-shaped. Clearer receipts and budgets per question would make “pay for reasoning” feel like a product.

    The local layer is trusted more than it is isolated. Policy can constrain what ships; it cannot make local execution a full sandbox of an untrusted world.
