    How a Plan is declared

    The last three chapters treated a Plan as a kitchen line: an ordered sequence of stations that consume and produce artifacts. This short chapter is the recipe card for that line — a YAML file that answers one question: in what order must artifacts exist?

    You need this only if you are adding a Plan, rearranging stations, or debugging why a derived artifact did not run. Product decisions — whether a station is optional, whether its dish appears on the canvas — do not live here. They live next to the catalog, in code, because they are about what the product offers, not about dependency order.

    What the file is

    Each YAML file in cloud_api/app/generation/plans/config/ declares one Plan. Every file uses the same schema; only the entries under artifacts differ.

    At startup the Cloud API loads all of these files and registers each graph by the plan_id inside it. The file name is a convenience. Convention is {capability}.{engine}.yaml — for example data_analysis.pandas.yaml — but the authoritative id is the field in the file.

    Think of the YAML as a bill of materials, not a program. It says “the computation graph depends on the Pandas code” the way a recipe says “the icing goes on after the cake.” It does not say “icing is optional if the guest declined dessert.” That second sentence is a request option, and request options are product behavior.

    The schema

    plan_id: <capability>/<engine>
terminal_stage: <stage_id>        # always runs last; implemented in Python

artifacts:
  - kind: <artifact_kind>         # stable id this stage produces
    stage: <stage_id>             # station implementation id
    depends_on: [<artifact_kind>] # direct dependencies only (may be [])
    Key Required Meaning
    plan_id yes Plan identifier; must match the Capability catalog
    terminal_stage yes Final station (persists results after per-call credit charges). Not listed under artifacts.
    artifacts yes Ordered list of station / artifact entries

    Each artifacts entry:

    Field Required Meaning
    kind yes Artifact kind produced by stage
    stage yes Registered station id on the Capability
    depends_on yes Artifact kinds that must exist before this station runs

    Validation and other internal steps are ordinary entries in this list. The YAML does not mark them “internal.” Canvas visibility — whether the desktop shows the dish — is configured in plan_behavior.py, next to the catalog.

    An example: validating the graph

    validate_dag checks the dag artifact and produces an internal analysis object the desktop never renders. In YAML that is only a dependency:

      - kind: analysis
    stage: validate_dag
    depends_on: [dag]

    Whether this station runs at all depends on whether you asked for the graph. That gate is not in this file.

    How dependencies are interpreted

    List only direct dependencies in depends_on. The loader checks that every referenced kind appears in the same file.

    Independent branches (same depends_on) run in YAML list order once their dependencies are satisfied. If a dependency was requested but not produced — an optional station failed — dependent stations are skipped automatically rather than run on missing input.

    Adding a new Plan

    1. Copy an existing YAML file and set a new plan_id.
    2. Fill artifacts with kind, stage, and depends_on only.
    3. Register station behavior (optional flags, request options, canvas artifacts) next to the catalog (plan_behavior.py).
    4. Register the Plan on the Capability.
    5. Implement any new stage ids on the Capability module.

    Adjusting dependencies for an existing Plan is a YAML-only change. Changing which stations are optional, or which request option turns them on, is a Python-only change. Keeping those two questions in two places is deliberate: the recipe should not silently become the menu.
