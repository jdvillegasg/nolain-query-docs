    Plan artifact dependency graphs

    Each *.yaml file in plan config directory defines one Plan. Every file uses the same schema; only the entries under artifacts differ per plan.

    Runtime code loads all YAML files at startup and registers graphs by plan_id.

    File naming

    Use {capability}.{engine}.yaml (for example data_analysis.pandas.yaml). The authoritative id is the plan_id field inside the file.

    Schema (same for every plan)

    plan_id: <capability>/<engine>
terminal_stage: <stage_id>        # always runs last; implemented in Python, not listed under artifacts

artifacts:
  - kind: <artifact_kind>         # stable artifact id this stage produces
    stage: <stage_id>             # Celery stage implementation id
    depends_on: [<artifact_kind>] # direct dependencies only (may be [])

    Top-level keys

    Key Required Meaning
    plan_id yes Plan identifier (must match capability catalog)
    terminal_stage yes Final stage id (persists results after per-LLM credit charges)
    artifacts yes Ordered list of stage/artifact entries

    artifacts entry fields

    Field Required Meaning
    kind yes Artifact kind produced by stage
    stage yes Registered stage id in the capability
    depends_on yes Artifact kinds that must exist before this stage runs

    YAML is only for dependencies between plan stages. Do not put optional, request_option, or canvas in YAML — those are defined in Python (app/generation/plans/plan_behavior.py and the capability catalog).

    There is no separate gate_stages section. Validation or other internal steps are ordinary artifacts entries; their canvas visibility is configured in code.

    Dependency matrix

    For N artifact kinds there are N×(N−1) possible directed edges. List only direct dependencies in depends_on; the loader validates that every referenced kind appears in the same file.

    Independent branches (same depends_on) run in YAML list order once dependencies are satisfied. If a dependency was requested but not produced (optional stage failed), dependent stages are skipped automatically.

    Example: internal validation stage

    validate_dag validates the dag artifact and produces internal analysis (not a desktop view). Dependencies only:

      - kind: analysis
    stage: validate_dag
    depends_on: [dag]

    Optional behavior and canvas visibility for this stage live in plan_behavior.py.

    Adding a new plan

    1. Copy an existing YAML file and set a new plan_id.
    2. Fill artifacts with kind, stage, and depends_on only.
    3. Register stage behavior (optional flags, request options, canvas artifacts) in plan_behavior.py.
    4. Register the plan in the capability catalog.
    5. Implement any new stage ids in the capability module.

    Adjusting dependencies for an existing plan requires editing YAML only. Changing optional stages or request-option gating requires editing Python only.
