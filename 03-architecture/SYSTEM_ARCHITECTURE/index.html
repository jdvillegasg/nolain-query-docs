    The parts of the system

    The previous chapter explained why nolainquery is split the way it is. This chapter is a map of what sits on each side of that split: the desktop, the local engine, the Cloud API, and the generation pipeline that turns an admitted question into artifacts.

    If you have not read The system philosophy, start there. The words Capability, Plan, Stage, artifact, sketch, and intent are used here with the meanings that chapter introduced.

    This chapter defines the running components, their boundaries, the generation framework, retry budgets, and the repository map. The next chapter owns the request-by-request walkthrough.

    Two machines, one question

    When you ask “What is total revenue by country?” two processes on your computer talk to a third process in the cloud.

    The desktop app is what you see: file picker, question bar, results table, chart canvas. It does not compute the answer itself. It asks a local helper to describe the file, asks the Cloud API to produce a recipe, then asks the helper to run that recipe.

    The local engine is that helper (a small Python service on port 8001). It is the only process that opens the file. It derives the sketch (column names, types, summaries, samples) and later executes the artifacts the cloud returned.

    The Cloud API is the remote reasoning service (port 8000 in development). It never receives the file. It receives the question plus the sketch, decides whether to generate anything, and — if so — returns artifacts.

    Around the Cloud API sit four supporting services:

    • Redis — short-lived memory for conversation sessions and generation jobs.
    • A background worker (Celery) — runs the Plan’s stages so the HTTP server does not block on model calls.
    • Supabase — who you are, whether your key is valid, how many credits remain.
    • OpenRouter — the single gateway for every language-model call. The product does not speak to OpenAI, DeepSeek, or anyone else directly.

    A health endpoint (GET /health) reports whether Redis, the worker, and Supabase are reachable. Generation refuses to start (503) if Redis or the worker is down.

    The generation framework

    The control plane does not have an open-ended “do data science” prompt. It has a menu, a kitchen line, stations, and dishes. Those four ideas are Capability, Plan, Stage, and Artifact.

    Menu, line, station, dish

    A restaurant is a useful picture:

    In the restaurant In nolainquery Today
    An item on the menu Capability — a product the cloud knows how to generate data_analysis: descriptive analysis of one CSV or Parquet file
    A kitchen line that prepares that item Plan — an engine: an ordered pipeline of stages data_analysis/pandas (implemented). data_analysis/ibis is on the menu but not staffed
    A station on that line Stage — a unit that consumes and produces artifacts Write the code; optionally compile a graph; optionally write a chart contract; validate; finish
    A dish that leaves a station Artifact — a typed output the desktop can use Executable Pandas code, optional computation graph, optional chart contract

    A few consequences of this picture, which the rest of the system depends on:

    • Intent is not on the menu. Intent is the maître d’ deciding whether you sit down, get a glass of water from memory, or get sent to the kitchen. Mixing intent with Capability would let the maître d’ invent new dishes.
    • A chart is a side, not a second menu item. You toggle it on the same Plan. There is no “visualization Plan.”
    • Semantic analysis is a conversation with the waiter, before the ticket reaches the kitchen. It is not a Capability.
    • The chef does not redesign the line. Policy rebuilds the Plan from the registry and from your toggles (the admission step in cloud_api/app/generation/policy.py).

    Optional artifacts on the Pandas Plan:

    Your toggle What you get
    Compile DAG (default on) A computation-graph artifact (dag)
    Dashboard / chart (default on) A chart contract (visualization_spec)

    The live menu is GET /api/v1/capabilities. Capabilities register themselves when the generation package loads.

    What the Pandas line produces

    The primary dish is always executable analysis (code_pandas, returned to clients as pandas_code). Everything else is optional and derived.

    Station Consumes Produces Calls a model? Optional?
    Write Pandas code — code_pandas Yes No. Static sandbox check; no execution on the server
    Compile DAG code_pandas dag Yes Yes, if you asked for the graph
    Format visualization code_pandas visualization_spec Yes Yes, if you asked for a chart
    Validate visualization visualization_spec internal check No With the chart
    Validate DAG dag internal check No With the graph
    Finalize code_pandas — No No. Persists produced artifacts after per-call charges

    Dependencies between stations — “the graph cannot be compiled before the code exists” — are declared in a YAML recipe card. That card is the subject of How a Plan is declared. Whether a station is optional, and whether its dish appears on the canvas, is a product decision and lives next to the catalog, not in the recipe.

    When code is regenerated (sandbox retry or runtime repair), derived dishes are thrown away and cooked again if you still asked for them. An old graph attached to new code would lie about what ran.

    How many model calls a job tends to make

    These counts are the worker stations only. Classification and semantic reading, if they ran, are extra conversation-side calls.

    Options Typical worker model calls
    Pandas only 1 (+ repairs if local execution fails)
    Pandas + graph 2 (code + compile); extra retries are separate budgets
    Pandas + chart, no graph 2
    Pandas + graph + chart 3 or more

    Retry budgets

    Retries are not one pool. Each failure mode has a different fix, so each has its own budget (configured in cloud_api/app/config/generation.yaml):

    Budget Spent when Default
    Sandbox retries The worker rejects truncated, empty, or statically illegal code before it ships 2
    Syntax-repair retries Generated code still has invalid syntax after deterministic delimiter repair 1
    Runtime-repair jobs The code shipped, the desktop ran it, and the real file threw an error 2
    Compile / chart retries Graph or chart compilation or validation failed 2
    Chain-wide ceiling Any Pandas generate-or-repair call, across the whole chain 9

    A repair selects a profile by the kind of failure (syntax, Unicode, sandbox policy, runtime, truncation, …) and how many times it has already been tried. Surgical categories emit with reasoning disabled so hidden tokens cannot empty the completion. Runtime-repair jobs get a fresh sandbox budget so a depleted in-cloud budget cannot block a new attempt; they inherit the chain-wide attempt count so nested jobs cannot multiply forever.

    Dialogue boundary

    Conversation routes sit in front of generation. A normal message incurs a classifier model call even when the final branch is a metadata answer, refusal, or explanation. If classification or its model fails, the route returns HTTP 503; no fail-open generation occurs. Clarification replies are the explicit shortcut: they bypass classification and semantic analysis and proceed to server-side Plan admission.

    The classifier may suggest a registered Capability and Plan, but policy rebuilds the Plan from the registry and client options. The concrete branches and their HTTP responses belong in A conversation from start to finish.

    Authentication and credits, in one paragraph

    Every workflow endpoint requires an API key (X-API-Key). Conversation routes check that credits remain without charging; each model call is charged the moment it completes. Portal-linked keys with an empty balance return HTTP 402. Unlinked non-developer keys return 402. Unlinked owner developer keys skip credit checks. Details: Credits. Portal account routes (/api/auth/*) use a Supabase sign-in token instead of the API key.

    Job memory

    A generation job lives in Redis for one hour (job_state:{job_id}). A conversation session lives for 24 hours (conversation:{session_id}). The desktop polls GET /api/v1/get_task_status/{task_id} for progress. Useful statuses include queued, generating_code, compiling_from_code, formatting_visualization, validating, finalizing, success, failed, and cancelled. Cancellation is cooperative between stages; model calls already completed stay charged.

    How to read a job — retries, token totals, credit receipts, worker logs — is covered in Calling the Cloud API and maintainer documentation (docs-private/).

    Two APIs for the same Capability

    Door What it is for
    Conversation (/api/v1/conversation/*) The desktop product: session, classification, clarification, local repair
    Direct generation (POST /api/v2/generate_dag) The same Capability without a chat: admit, synthesize, return artifacts
    Legacy (POST /api/v1/generate_dag) An older planner → compiler chain that does not use the Capability registry

    Other useful endpoints: the model catalog (GET /api/v1/llm/models), the Capability catalog (GET /api/v1/capabilities), and standalone semantic analysis (POST /api/v1/analyze_query). Full request shapes and curl examples: Calling the Cloud API.

    Current product boundary

    out_of_scope is doing real work: the classifier sees the live catalog, and anything the catalog cannot serve returns a text message and does not admit generation. The Ibis Plan is the next engine for the same product, not a second product. It is catalogued and rejected until implemented.
