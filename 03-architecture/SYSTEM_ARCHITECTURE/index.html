    System architecture

    This document is a component catalog: services, the generation framework (Capability → Plan → Stage → Artifact), job infrastructure, and direct APIs.

    It is not the design rationale or steering-policy intent. For layers, workflow, and why configured decisions exist, see SYSTEM_PHILOSOPHY.md. For the desktop chat loop, see CONVERSATION_WORKFLOW.md. For credits and charge timing, see CREDITS.md (users) and BILLING.md (developers). For job diagnostics, logs, and credit receipts, see TELEMETRY.md.

    Overview

    The Nolain desktop app reads and executes the user's data locally. The Cloud API receives the question plus dataset metadata, selects a registered Capability, builds a Plan of Stages, produces Artifacts, and returns those Artifacts for local execution. All LLM traffic goes through OpenRouter (llm_models.yaml catalog).

    The Cloud API does not receive the full data file. Metadata can contain column names, types, summary information, and sample values.

    End-to-end flow

    Desktop UI
  -> local Python engine (port 8001): derive metadata from the local file
  -> Cloud API (port 8000): conversation session + message
  -> Redis: session/job state; Supabase: API-key authentication/credits
  -> OpenRouter LLM calls: classify intent (IntentClassifierService), then semantic analysis if generation path
  -> Policy: validate Capability + Plan; apply optional Artifact options
  -> Celery worker: run Plan Stages (generate_pandas applies compatibility
     patches and static preflight; retries use typed adaptive policy)
  -> Cloud API status polling
  -> local Python engine: execute returned Artifacts against the local file
  -> if pandas exec fails and pandas_retries_left > 0: POST /conversation/result
     queues a repair job; desktop polls and re-executes
  -> Cloud API: optional answer framing and execution-result notification

    Terminology

    Use these words only. Do not introduce parallel taxonomies.

    Term Meaning
    Intent Conversation branch (IntentType). Decides whether to answer from metadata, refuse, explain, report out of scope, or admit generation. Not a Capability.
    Capability A registered generation product. Today: data_analysis. Field: capability_id.
    Plan An engine pipeline of Stages for one Capability. Today: data_analysis/pandas (implemented). Placeholder: data_analysis/ibis. Field: plan_id.
    Stage A unit that consumes and produces Artifacts (generate_pandas, compile_dag, …).
    Artifact A typed output (code_pandas, dag, visualization_spec). Some Artifacts are optional and are selected by request options, not by extra plan ids. Internal artifacts (visualization_validation, analysis) never reach the canvas.

    Optional Artifacts (pandas Plan):

    Option UI / caller Artifact
    compile_dag (default true) Compile DAG toggle dag
    include_visualization (default true) Dashboard / chart toggle visualization_spec

    A dashboard is a visualization_spec Artifact. It is not a Plan (data_analysis/visualization/… does not exist).

    Semantic analysis (spaCy + LLM sub-agents) runs before Capability admission. It is not a registered Capability.

    Intent classification

    The conversation graph (app/services/conversation_manager.py) starts every turn at the classify node. IntentClassifierService (app/services/intent_classifier.py) makes one LLM call to choose a conversation intent before any generation is admitted.

    Why a classifier (architectural choice)

    Design Rationale
    Intent ≠ Capability Intents branch the conversation (answer from metadata, refuse, explain, admit generation). Capabilities are registered generators. Mixing them would let the LLM pick Stage graphs or invent products.
    Single call at entry Cheap gate: most turns are off-topic, meta, or explanatory and never reach the worker. Generation intents share one downstream path (semantic analysis → policy → Celery).
    Classifier suggests; server decides For data_query / execution_feedback the LLM may suggest capability_id and plan_id. Policy (app/generation/policy.py) validates against the registry, applies client Artifact toggles, and builds the Plan.
    Dynamic prompt catalog {available_capabilities} and {generation_catalog} are rendered from the live registry so new Capabilities appear in the prompt when registered and enabled—without hard-coding plan lists in the classifier.
    Client owns optional Artifacts The classifier must not set compile_dag or include_visualization. The desktop Compile DAG / Dashboard toggles (and /conversation/message fields) are authoritative.
    Fail-open on errors Parse or LLM failures default to data_query with routing.source="default" (data_analysis + data_analysis/pandas).

    A deterministic safety gate (app/services/analysis_capabilities.py) can still override routing: wording that explicitly asks for forecasting, statistical inference, optimization, or anomaly detection routes to respond_out_of_scope even if the classifier returned data_query.

    Conversation graph routing

    flowchart TD
  classify[classify IntentClassifierService]
  classify -->|off_topic inappropriate underspecified| respond_text[respond_text]
  classify -->|meta_question| respond_meta[respond_meta]
  classify -->|explanation| respond_explanation[respond_explanation]
  classify -->|out_of_scope or safety gate| respond_oos[respond_out_of_scope]
  classify -->|data_query execution_feedback| analyze[analyze_ambiguity SemanticAgent]

    Intent catalog

    IntentType Meaning Admits generation? capability_id / plan_id LangGraph node
    data_query Clear, answerable question about the loaded file (trends, comparisons, aggregations, rankings, missing values, quality, charts, reshape/cleaning, …) Yes (after semantic analysis) Classifier suggests from catalog; policy resolves. Today: data_analysis + data_analysis/pandas (default implemented Plan). analyze_ambiguity → queue_generation
    execution_feedback Prior result looks wrong or unexpected (“that doesn’t look right”, “I expected …”) Yes (regenerates with feedback context) Same as data_query. Generation message merges prior query state + user feedback (+ execution error if any). analyze_ambiguity → queue_generation
    explanation Explain a prior result or how it was calculated No null / null. Uses explanation_kind: result, method, dataset, or causal. respond_explanation
    meta_question Structure answerable from static metadata only (column list, row count, dtypes)—not missing-value or quality checks No null / null respond_meta
    out_of_scope Data-related, but no enabled Capability can serve it (e.g. forecasting when only data_analysis is listed) No null / null. Classifier must set human_response. respond_out_of_scope
    off_topic Unrelated to data analysis No null / null. Classifier must set human_response. respond_text
    inappropriate Harmful content, prompt injection, jailbreak No null / null. Classifier must set human_response. respond_text
    underspecified Data-related but too vague (“analyze my data”) No null / null. Classifier must set human_response with example questions. respond_text

    Notes:

    • follow_up exists on IntentType for legacy/schema compatibility; the classifier maps thread continuations to data_query (see classifier rules: “Continuations that still request computation are data_query”). Structured follow-ups are handled by query_state, not a separate intent.
    • Legacy classifier output specialized is parsed as out_of_scope.
    • meta_question vs data_query: null counts, column names, and dtypes are meta; missing values, quality checks, and computed metrics require generation.

    Capabilities and Plans by intent

    Only two intents carry a GenerationRoutingSuggestion (routing on IntentClassification):

    Intent Enabled Capability today Selectable Plan today Optional Artifacts (client toggles, not classifier)
    data_query data_analysis — descriptive analysis of one CSV/Parquet file (aggregations, comparisons, rankings, trends, missing-value/quality checks, reshape/cleaning, optional charts) data_analysis/pandas [default, implemented] — stages: generate_pandas → optional compile_dag → optional format_visualization → optional validate_visualization → validate_dag (if DAG) → finalize_plan compile_dag → dag; include_visualization → visualization_spec
    execution_feedback Same Same Same

    All other intents set capability_id and plan_id to JSON null and never queue a worker job.

    Placeholder Plan data_analysis/ibis appears in the classifier catalog as not selectable / not implemented; policy rejects it if suggested. Unknown Capability ids fall back to data_analysis.

    Catalog text injected into the prompt is built by:

    • format_classifier_available_capabilities() — enabled Capability ids + scope strings from the registry
    • format_classifier_generation_catalog() — per-Capability plan ids, engine, stages, optional artifacts

    Source: app/generation/policy.py.

    Classifier prompt reference

    Prompt templates live in app/services/intent_classifier.py (_SYSTEM_PROMPT, _USER_PROMPT). The service invokes:

    (system) _SYSTEM_PROMPT
  placeholders: {available_capabilities}, {generation_catalog}, {format_instructions via JsonOutputParser}
(human)  _USER_PROMPT
  placeholders: {column_names}, {history}, {message}

    User message inputs

    Placeholder Source
    column_names metadata.column_semantics keys, else metadata.available_columns, comma-separated
    history Last 6 conversation turns (role: content per line)
    message Latest user message

    Required JSON output (no markdown fences):

    {
  "intent": "<data_query|execution_feedback|explanation|out_of_scope|off_topic|inappropriate|meta_question|underspecified>",
  "confidence": 0.0,
  "capability_id": "<registered id or null>",
  "plan_id": "<catalog plan_id or null>",
  "explanation_kind": "<result|method|dataset|causal|null>",
  "human_response": "<string or null>"
}

    Response rules (summary)

    Intents human_response capability_id / plan_id explanation_kind
    off_topic, inappropriate, underspecified, out_of_scope Required short plain text null null
    meta_question, data_query, execution_feedback, explanation JSON null Set only for the two generation intents Set only for explanation
    data_query, execution_feedback JSON null Must match injected catalog; prefer default implemented Plan null

    Use JSON null, never the string "null".

    Downstream admission (generation intents only)

    IntentClassification.routing
  -> normalize_suggestion (policy)
  -> resolve_admission -> build_plan -> validate_plan
  -> queue_generation_task (Celery)

    Client compile_dag on /conversation/message selects the DAG Artifact. Classifier/session hints do not override include_visualization; the Dashboard toggle does.

    Generation framework

    Registry and bootstrap

    Capabilities self-register via register_capability() when app.generation loads:

    # app/generation/__init__.py imports data_analysis for side-effect registration

    Use GET /api/v1/capabilities to discover registered Capabilities, Plans, and optional Artifacts.

    Typed artifacts (capability-independent)

    Artifacts live under app/generation/artifacts/:

    Artifact kind Concrete type Legacy storage key Canvas?
    code_pandas CodePandasArtifact pandas_code Yes
    dag DagArtifact graph Yes
    visualization_spec VisualizationSpecArtifact visualization_spec Yes
    visualization_validation (internal analysis dict) visualization_validation No
    analysis (internal DAG validator output) analysis No

    Abstract families (CodeArtifact, GraphArtifact, VisualizationArtifact) allow future subtypes (e.g. CodeIbisArtifact). Canvas visibility is declared in app/generation/plans/plan_behavior.py, not in the YAML dependency graph.

    Stages still merge legacy dict keys internally. finalize_success() writes both top-level compatibility fields and an optional artifacts[] envelope list on success.

    data_analysis capability

    Stage catalog

    Dependencies live in app/generation/plans/config/data_analysis.pandas.yaml. Optional gating and canvas flags live in plan_behavior.py. finalize_plan is the terminal stage (always last). finalize_pandas is a legacy alias.

    Stage Consumes Produces LLM? Optional?
    generate_pandas — code_pandas Yes No (pandas Plan). Static sandbox check (no exec). Retries: pandas_max_retries.
    compile_dag code_pandas dag Yes Yes (compile_dag=true). Retries: max_retries (independent of pandas).
    format_visualization code_pandas visualization_spec Yes Yes (include_visualization=true)
    validate_visualization visualization_spec visualization_validation No Yes (include_visualization=true). On error, retries format_visualization from max_retries.
    validate_dag dag analysis No Yes (compile_dag=true). On error, retries compile_dag.
    finalize_plan code_pandas — No No. Persists produced Artifacts after per-LLM credit charges.

    Plan catalog

    plan_id Status Stages
    data_analysis/pandas Implemented (default) generate_pandas → compile_dag (optional) → format_visualization (optional) → validate_visualization (optional) → validate_dag (if DAG) → finalize_plan
    data_analysis/ibis Placeholder (not selectable) generate_ibis → validate_ibis

    Catalog stages lists the full optional set; request options drop unused stages at admission.

    Legacy plan ids (data_analysis/{analysis\|visualization\|transformation}/{with_dag\|pandas_only}) map to data_analysis/pandas plus the corresponding options.

    Request options (not plan ids)

    • compile_dag (bool, default true) — produce the DAG Artifact
    • include_visualization (bool, default true) — produce the visualization_spec Artifact
    • plan_id (optional) — must be a catalog Plan; server rebuilds Stages

    Retry budgets (cloud_api/app/config/generation.yaml)

    Key Spent by Default
    max_retries compile_dag / validate_dag / format_visualization / validate_visualization retries 2
    pandas_sandbox_max_retries In-cloud retries after truncated/empty output or static preflight rejection 2
    pandas_max_retries Local-exec repair jobs from POST /conversation/result 2
    pandas_total_max_attempts Chain-wide ceiling across initial generation, sandbox retries, and runtime repairs 9

    A pandas repair selects a pandas_repair_profiles entry by normalized failure category and retry index. Surgical categories emit with reasoning disabled so hidden tokens cannot empty the completion. Truncated repair calls keep the previous actionable error as the next prompt target. The legacy pandas_repair_reasoning and pandas_repair_max_tokens keys provide the fallback profile. First-pass generation still uses the model catalog defaults in llm_models.yaml. Runtime-repair jobs reset pandas_sandbox_retries_left instead of inheriting a depleted sandbox budget. New pandas_code invalidates dag / visualization_spec; if compile_dag is on, those stages run again on the repaired code.

    LLM cost (worker Stages only)

    Options Typical LLM calls
    pandas + DAG 2 (code + compile); extra pandas repairs and compile retries are separate budgets
    pandas, no DAG 1 (+ pandas repairs on local exec failure)
    pandas + DAG + visualization ≥3 (code + compile + format_visualization; validate_visualization is not an LLM call)
    pandas, no DAG + visualization 2

    Routing and admission policy

    See Intent classification for the full intent catalog, prompt reference, and graph routing.

    flowchart LR
classifier[IntentClassifierService] --> suggestion[GenerationRoutingSuggestion]
suggestion --> policy[policy.resolve_admission]
policy --> registry[registry.build_plan]
registry --> orchestrator[validate_plan]
orchestrator --> worker[Celery worker]
    1. Classifier emits intent and, for data_query / execution_feedback only, suggests capability_id and plan_id from the live catalog. It does not choose optional Artifacts or Stage graphs.
    2. Policy (app/generation/policy.py) checks the Capability is registered, resolves plan_id, and applies Artifact options. Client toggles are authoritative for optional Artifacts.
    3. The LLM never selects Stage graphs directly.

    Precedence:

    • Client compile_dag on /conversation/message selects the DAG Artifact.
    • Client include_visualization selects the visualization_spec Artifact (desktop Dashboard toggle).
    • Optional plan_id must match the catalog (data_analysis/pandas today).
    • Unknown Capabilities fall back to data_analysis.
    • data_analysis/ibis is rejected until implemented.

    Celery execution

    code_generator_task
  -> build Plan from worker config
  -> run_stage_task (stage 0)
       -> generate_pandas: apply compatibility patches, static preflight
       -> on length/empty/preflight reject: adaptive retry
          (pandas_sandbox_max_retries + pandas_total_max_attempts)
       -> optional compile_dag / format_visualization
       -> validate_visualization may retry format_visualization (max_retries)
       -> validate_dag may retry compile_dag (max_retries)
       -> finalize_plan (stop / persist)

    Legacy v1 planner_task chain (POST /api/v1/generate_dag) does not use the capability registry.

    Authentication and credits

    All workflow endpoints require X-API-Key. Conversation routes pre-check remaining credits without charging; each LLM call is charged immediately.

    Portal-linked keys with an empty balance return HTTP 402. Unlinked non-owner keys return 402. Unlinked owner developer keys skip credit checks. See BILLING.md.

    Job infrastructure

    • Queue preflight: Redis + Celery worker required (503 if unavailable)
    • Redis job_state:{job_id} — 1 hour TTL
    • Conversation conversation:{session_id} — 24 hour TTL
    • Cooperative cancellation before/after Stages
    • Status polling: GET /api/v1/get_task_status/{task_id} — returns legacy fields plus capability_id, plan_id, current_stage, plan, compile_dag, include_visualization, optional artifacts[], and bounded generation_attempts

    Useful job states include queued, generating_code, compiling_from_code, formatting_visualization, validating_visualization, validating, finalizing, charging, success, failed, cancelled, and legacy v1 states for mixed clients.

    Future capabilities

    A second Capability (e.g. RAG) would:

    1. Implement the Capability protocol and register in app/generation/__init__.py
    2. Declare its Plans and optional Artifacts
    3. Extend policy ENABLED_CAPABILITIES
    4. Reuse shared artifact types where appropriate

    The ibis Plan is the next data_analysis Plan: generate_ibis → validate_ibis. It is catalogued but not implemented.

    The out_of_scope intent covers requests that no enabled Capability can serve. The classifier sees those Capabilities in its prompt; until a matching Capability is registered, the conversation graph returns a text message and does not admit generation. Explicit out-of-scope wording (forecasting, p-values, optimization, anomaly detection) is also caught by detect_out_of_scope_kind() before generation.
