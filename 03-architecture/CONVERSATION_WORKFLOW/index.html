    A conversation from start to finish

    The last two chapters explained the design and named the parts. This chapter is the desktop product in motion: what happens, request by request, from the moment you load a file to the moment a table (and maybe a chart) appears.

    The path described here is Ask Queries. There is a second door — direct generation without a chat — that covers only the middle of this story (produce artifacts, poll, execute). It does not classify, clarify, or repair. Both doors produce the same Capability. This chapter is the full loop.

    You will see HTTP paths. They are the messages on the wire, not the entry point for the ideas. The ideas are: open a session on a sketch, decide what kind of turn this is, maybe generate, execute locally, report back, repair if needed, optionally narrate.

    The loop at a glance

    Seven moves. The rest of the chapter walks each one, then shows what changes if the question is off-topic, ambiguous, or fails on the real file.

    1. Start a session with the current sketch. No model call, no charge.
    2. Send the question (and your graph/chart toggles). The server classifies the turn and either replies immediately or admits a generation job.
    3. Poll the job until artifacts are ready (or the job fails).
    4. Execute locally on the engine that has the file.
    5. Report the outcome. On success, the result is stored for follow-ups. On failure with budget remaining, the server queues a repair.
    6. If repairing, poll and execute again until the run succeeds or the budget is exhausted.
    7. Optionally ask for a narrative wrapping of the numbers.

    Two kinds of Pandas retry share a chain-wide ceiling (default 9 generate-or- repair calls) but spend different source budgets:

    Kind When Where it happens
    Sandbox retry Truncated, empty, or statically illegal code during cloud generation Inside the worker, before anything ships
    Runtime repair Code passed those checks but failed when executed locally After you report the error; a new job, no new classification

    Compiler and chart retries are a third budget and are not spent here.

    What you need before the first message

    • The desktop has asked the local engine for a sketch (POST http://localhost:8001/data_summary).
    • Requests carry a valid API key (X-API-Key).
    • Sessions are reused until the desktop resets local state. On the server they expire after 24 hours.

    A worked example

    Suppose the loaded file has columns Invoice, Quantity, Price, Country, and you ask:

    What are the top 5 countries by total revenue?

    You have left both toggles on: compile a computation graph, and produce a chart.

    1. Start a session

    The desktop posts the sketch and receives a session_id. Nothing is classified. Nothing is charged. Redis now holds conversation:{session_id} — a short-lived thread bound to that sketch.

    2. Send the question

    The desktop posts the session id, the question, the sketch, and the toggles. Without a clarification payload, the conversation graph runs:

    1. Classify the turn (one model call). For this question the kind is a data question.
    2. Read the wording for ambiguities (semantic analysis). “Revenue” might mean Quantity * Price, or it might mean something else in your file. If the reading is ambiguous, you get a clarification and the loop waits. If it fails, you get a text reply and no job.
    3. If the reading is clear, policy admits the Pandas Plan with your toggles and queues a worker job.

    The response type tells the desktop what to do next:

    Response type Meaning What the desktop does
    text_response Off-topic, unsafe, underspecified, explanation, out of scope, or fallback Show the text
    meta_answer Question about the file’s structure Show the metadata answer
    clarification Ambiguous terms Resend with your chosen interpretations
    generation Job accepted Poll task_id

    A generation response also echoes capability_id, plan_id, and the toggles the server actually admitted, so the desktop can show what was queued.

    Clarification shortcut. When you resend with clarifications filled in, classification and semantic reading are skipped. The meaning of the question is treated as settled; the server queues the Plan with the current toggles.

    What the classifier is allowed to do. It chooses the kind of turn. For generation kinds it may suggest a Capability and a Plan from the live catalog. It does not turn the graph or the chart on or off. Those are your toggles. Policy, not the prompt, rebuilds the pipeline.

    3. Poll the job

    The desktop asks for status about every 1.5 seconds. When the pipeline status is success or failed, the job is done.

    The payload that matters for the rest of the loop:

    • pandas_code — the program to run locally
    • optional graph and visualization_spec — if you asked for them and those stations succeeded
    • pandas_retries_left — remaining local repair jobs
    • pandas_sandbox_retries_left — remaining in-cloud static retries
    • pandas_attempts_used / pandas_total_max_attempts — chain-wide usage and ceiling
    • billing.charged_credits — running total for worker model calls
    • generation_attempts — per-call diagnostics (finish reason, selected repair profile, tokens, accepted or rejected)

    While the job runs, the worker may retry writing the code internally (truncated completion, empty extract, static sandbox reject). Partial length-limited code is never sent for execution.

    4. Execute locally

    Execution is on the local engine (port 8001), never on the Cloud API:

    • run the Pandas code against the loaded file
    • if a graph artifact is present, run that too

    No cloud credit is charged for this step. This is the first moment the analysis meets the rows.

    5. Report the outcome

    After every local run — success or failure — the desktop tells the conversation what happened, so follow-up questions have execution context.

    Success. The server stores the result and returns { "status": "ok" }. Later, “how did you calculate that?” can be answered from this memory without generating again.

    Failure with budget remaining. If the error and the failed code are both present, the previous job succeeded on the cloud side (it shipped code), and pandas_retries_left is still positive, the server:

    1. Reads the remaining budget from that job
    2. Queues a new generate-and-repair job with the failed code and the error (no new classifier, no new semantic turn)
    3. Decrements the runtime-repair budget on the new job
    4. Resets the in-cloud sandbox budget for that repair (so a depleted sandbox count cannot block a new attempt) and carries the chain-wide attempt count forward (so repairs cannot multiply forever)
    5. Returns { "status": "repairing", "task_id": "..." }

    The desktop then repeats poll → execute → report with the new task id. If no retries remain, the server returns { "status": "ok" } and the desktop keeps the error.

    Repair settings are chosen from the kind of failure and the retry index (syntax vs runtime vs truncation, first try vs repeated signature). All Pandas generate-or-repair calls remain bounded by the chain-wide ceiling.

    6. Optional narrative

    After a successful execution, the desktop may ask the cloud to frame the numbers as a short paragraph. That is another model call, charged if it runs. If it fails, the endpoint still returns an empty narrative: you keep the table.

    The same loop, other kinds of turn

    The revenue question was the happy path. Dialogue exists so that not every message takes it.

    What you asked What the server does Credits
    “What’s the weather?” / jailbreak / “analyze my data” Classify → text reply Charged if that path called a model
    “What columns do I have?” Classify → answer from the sketch Free when no model is called
    “How did you calculate that?” Classify → grounded text from stored result Charged if that path called a model
    “Forecast next quarter’s sales” Classify or safety net → named refusal Charged if that path called a model
    Clear data question Classify → semantic reading → generation Per model call in the job
    Ambiguous data question Classify → semantic reading → clarification Per model call already made
    Your reply to a clarification Skip classify/semantic → generation Per model call in the job
    “That doesn’t look right” Always semantic reading → generation Per model call in the job
    Local Pandas error, retries left Report → repair job Per model call in the repair job
    Local execution Desktop port 8001 No cloud charge
    Answer framing Optional synthesize Per model call

    What the product will and will not do

    • Data questions — including charts and reshape — admit the Pandas Plan. Charts set the visualization toggle; they do not change which Plan you are on.
    • Requests no registered Capability can serve return a text message naming what is available, and do not admit generation. A wording-based safety net still catches forecasting, statistical inference, optimization, and anomaly detection while only descriptive analysis is enabled.
    • Explanation requests use saved result context and do not queue generation.

    The HTTP surface, as a table

    Once the story is clear, the endpoints are just names for the moves:

    Endpoint Move
    POST /api/v1/conversation/start Open a session on a sketch
    POST /api/v1/conversation/message Classify (or skip) and maybe admit a job
    GET /api/v1/get_task_status/{task_id} Poll generation
    POST /api/v1/conversation/result Store the local outcome; maybe queue repair
    POST /api/v1/conversation/synthesize Optional narrative
    GET /api/v1/conversation/{session_id} Read the session
    DELETE /api/v1/conversation/{session_id} Delete the session
    POST /api/v1/cancel_task/{task_id} Cooperative cancel between stages

    Session read and delete currently do not verify that the calling key created the session. Cancellation does: only the key that owns the job may cancel it. Model calls already completed keep their charges.
