    Cloud API conversation workflow

    This document describes the desktop Ask Queries conversation loop — the full path from session start through local execution and optional runtime repair. For platform architecture (Capability → Plan → Stage → Artifact), see SYSTEM_ARCHITECTURE.md. For job diagnostics, attempt logs, and credit receipts, see ../05-operations/TELEMETRY.md.

    Conversation loop

    The desktop app uses this end-to-end path. Direct generation APIs such as POST /api/v2/generate_dag cover only steps 3–4; they do not run the runtime repair loop in steps 5–6.

    1. POST /api/v1/conversation/start
     { metadata }
   → { session_id }

2. POST /api/v1/conversation/message
     { session_id, message, metadata, compile_dag?, plan_id?, ... }
   → text_response | meta_answer | clarification | generation { task_id, ... }

3. Poll GET /api/v1/get_task_status/{task_id}
   → pandas_code, optional dag / visualization_spec,
     pandas_retries_left, pandas_retries, billing, ...

4. Execute locally (desktop sidecar, port 8001)
   → POST /execute_pandas for pandas code
   → POST /execute_dag when a DAG Artifact is present

5. POST /api/v1/conversation/result
     { session_id, pandas_code?, exec_error?, exec_result?, dag? }
   → exec ok: { status: "ok" } — result stored for follow-ups
   → exec_error and pandas_retries_left > 0:
        { status: "repairing", task_id: "..." }

6. On repairing: repeat steps 3–5 with the new task_id until local
   execution succeeds or the pandas retry budget is exhausted.

7. Optional: POST /api/v1/conversation/synthesize
     { session_id, question, result_summary, outcome, ... }
   → framed narrative for the UI

    Two kinds of pandas retries use separate source budgets and share one chain-wide LLM-attempt ceiling:

    Kind When Where
    Sandbox retry Truncated/empty code or static policy reject during cloud generation Inside the Celery job at step 3 (generate_pandas stage); spends pandas_sandbox_max_retries
    Runtime repair Code passes generation but fails when executed locally Step 5 → new job at step 3 (POST /conversation/result); spends pandas_max_retries

    Both paths increment pandas_attempts_used and cannot exceed pandas_total_max_attempts (default 9: initial generation, its sandbox retries, and each runtime-repair job with a fresh sandbox budget). Compiler retries (max_retries in generation.yaml) remain independent.

    Prerequisites

    • The desktop app derives dataset metadata from the local engine (POST http://localhost:8001/data_summary).
    • Requests require a valid X-API-Key.
    • Sessions are reused until the desktop resets local state; server sessions expire after 24 hours.

    Vocabulary

    Term Role in this loop
    Intent Which conversation branch to take
    Capability Registered generator (data_analysis) once generation is admitted
    Plan Engine pipeline (data_analysis/pandas)
    Artifact Optional outputs (dag via Compile DAG; visualization_spec for charts)

    descriptive / visualization / transformation are not Capabilities or Plans.

    Stage 1 — Start session

    POST /api/v1/conversation/start
{ metadata }

    Creates conversation:{session_id} in Redis. No LLM call; no credit charge.

    Stage 2 — Send message

    POST /api/v1/conversation/message
{ session_id, message, metadata, provider?, model?, clarifications?, compile_dag?, plan_id? }

    compile_dag is the Compile DAG UI toggle (optional DAG Artifact). plan_id is optional; default is data_analysis/pandas.

    Without clarifications, LangGraph classifies intent:

    classify intent
  |- out_of_scope                              -> text_response (no matching Capability)
  |- off_topic / inappropriate / underspecified -> text_response
  |- meta_question                             -> meta_answer
  |- explanation                               -> grounded text_response
  |- execution_feedback                        -> semantic analysis -> queue generation
  `- data_query                                -> semantic analysis
                                              |- ambiguity -> clarification
                                              |- semantic failure -> text_response
                                              `- clear -> queue generation
                                                (data_analysis / pandas Plan;
                                                 optional Artifacts from request options)

    The classifier chooses intent using the registered Capabilities as prompt context. For generation intents it may suggest capability_id, plan_id, and include_visualization. Policy admits the Plan. Client compile_dag selects the DAG Artifact.

    Immediate response types

    Response type Meaning Client action
    text_response Off-topic, unsafe, underspecified, explanation, out of scope, or fallback Display text
    meta_answer Dataset-structure question Display metadata answer
    clarification Ambiguous terms Resend with clarifications
    generation Job accepted Continue to stage 3

    generation responses include task_id, capability_id, plan_id, compile_dag, and include_visualization.

    Clarification shortcut

    When clarifications is set, the graph is skipped. The server queues the pandas Plan with the current compile_dag option.

    Stage 3 — Poll generation job

    GET /api/v1/get_task_status/{task_id}

    The desktop app polls at ~1.5s intervals (up to ~80 attempts). When dag_status is success or failed, the job is done.

    Key fields for the repair loop:

    • pandas_code — code to execute locally
    • pandas_retries_left — remaining local-runtime repair jobs
    • pandas_sandbox_retries_left — remaining in-cloud static retries
    • pandas_attempts_used / pandas_total_max_attempts — chain-level LLM-call usage and ceiling
    • generation_attempts — bounded attempt diagnostics (finish reason, category, selected profile, token usage, and outcome)
    • pandas_retries — sandbox retries already used

    While the job runs, the worker may retry generate_pandas internally when a completion is truncated (finish_reason=length), empty, or rejected by static preflight. Partial length-limited code is never sent for execution.

    Stage 4 — Local execution

    Execution runs on the desktop sidecar (port 8001), not on the cloud API:

    • POST http://localhost:8001/execute_pandas — run generated pandas code against the loaded dataset
    • POST http://localhost:8001/execute_dag — run the DAG Artifact when present

    No cloud credit is charged for local execution.

    Stage 5 — Report result and runtime repair

    POST /api/v1/conversation/result
{ session_id, dag?, exec_result?, exec_error?, pandas_code? }

    After every local execution (success or failure), the client notifies the server so follow-up questions have execution context.

    Success

    When execution succeeds, the server stores the result and returns { "status": "ok" }.

    Runtime repair

    When exec_error and pandas_code are both set, the previous generation job succeeded (status=success), and that job still has pandas_retries_left > 0, the server:

    1. Reads the remaining budget from the previous job's state
    2. Queues a new generate_pandas repair job with the failed code and error in the bounded pandas_error_history (no new classifier or semantic turn)
    3. Decrements pandas_retries_left on the new job
    4. Resets the in-cloud sandbox retry budget for that repair job, and carries attempt history plus the chain-level attempt count instead of resetting them
    5. Returns { "status": "repairing", "task_id": "..." }

    The client then repeats stages 3–5 with the new task_id. If no retries remain, the server returns { "status": "ok" } and the client keeps the error.

    Repair settings are selected from pandas_repair_profiles by normalized error category and retry index. All Pandas generation calls remain bounded by pandas_total_max_attempts.

    Stage 6 — Optional synthesize

    POST /api/v1/conversation/synthesize
{ session_id, question, result_summary, outcome, ... }

    Optional answer framing after a successful execution. On failure, the endpoint returns { "status": "success", "narrative": {} }.

    Branch reference

    User case Server path Credit effect
    Off-topic / inappropriate / underspecified Classifier → text Charged if that path calls an LLM
    Meta question Classifier → metadata answer Free when no LLM is called
    Explanation Classifier → grounded text Charged if that path calls an LLM
    Out of scope (no matching Capability) Classifier or regex → text Charged if that path calls an LLM
    Clear data question Classifier → semantic → generation Credits per LLM call in the job
    Ambiguous question Classifier → semantic → clarification Credits per LLM call already made
    Clarification reply Bypass classify/semantic → generation Credits per LLM call in the job
    Execution feedback (“that looks wrong”) Always semantic → generation Credits per LLM call in the job
    Local pandas exec error with retries left Stage 5 → repair job Credits per LLM call in the repair job
    Local execution Desktop port 8001 No Cloud charge
    Answer framing Stage 6 synthesize Credits per LLM call

    Worker LLM cost details and Plan stage lists: SYSTEM_ARCHITECTURE.md.

    Supported analysis boundaries

    • Data questions (including charts and reshape) admit the data_analysis pandas Plan. Charts set include_visualization; they do not change plan_id.
    • Requests that no registered Capability can serve (out_of_scope) return a text message naming the available Capabilities and do not admit generation. A regex safety gate still catches forecasting, statistical inference, optimization, and anomaly detection while only data_analysis is enabled.
    • Explanation requests use saved result context and do not queue generation.

    Conversation endpoints

    Endpoint Behavior
    POST /api/v1/conversation/start Create session (stage 1)
    POST /api/v1/conversation/message Main decision + job admission (stage 2)
    GET /api/v1/get_task_status/{task_id} Poll generation job (stage 3)
    POST /api/v1/conversation/result Store local execution outcome; trigger repair (stage 5)
    POST /api/v1/conversation/synthesize Optional answer narrative (stage 6)
    GET /api/v1/conversation/{session_id} Read session
    DELETE /api/v1/conversation/{session_id} Delete session

    Session read/delete does not verify session ownership by API key (current behavior).

    Cancellation

    POST /api/v1/cancel_task/{task_id}

    Cooperative cancellation between Stages. LLM calls already completed keep their credit charges.
