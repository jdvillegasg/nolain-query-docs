    Telemetry

    This document is the catalog of observability the product actually emits: job progress, per-attempt generation diagnostics, token and latency totals, credit receipts, conversation session state, health pings, and structured logs.

    There is no OpenTelemetry SDK, Langfuse, Prometheus, Flower, Sentry, or third-party APM. Celery task_send_sent_event / Flower event streaming is not enabled. What exists is first-party state in Redis, a credit ledger in Supabase, Celery’s result backend, and Python logs.

    Related docs: SYSTEM_ARCHITECUTRE.md (pipeline), CONVERSATION_WORKFLOW.md (chat loop), BILLING.md (credits), CLOUD_API_USAGE.md (status payload).

    Processes

    Process How it runs (dev) What it emits
    Cloud API (FastAPI / Uvicorn, port 8000) scripts/launch-cloud-dev.sh HTTP health, conversation session Redis, classifier logs, per-call credit charges without a job id, status polling surface
    Celery worker (data_query_tasks) same launcher: celery -A app.core.celery_app worker --loglevel=info Redis job_state:{job_id}, Celery result backend, structured attempt logs, per-call credit charges with a job id
    Redis Docker from the launcher Job state (1 h TTL), conversation sessions (24 h TTL), Celery broker + result backend
    Supabase hosted Credit balance + credit_balance_ledger_nolain_query receipts
    Local Python engine (port 8001) launch.sh Execution results posted back to the Cloud API; no generation telemetry of its own
    Desktop (Tauri) launch.sh Polls job status; posts /conversation/result; does not persist worker diagnostics locally

    OpenRouter is the LLM gateway. Token counts and finish_reason come from LangChain AIMessage.usage_metadata / response_metadata after each invoke. The app does not scrape OpenRouter’s dashboard.

    Stores

    Celery worker / Cloud API
  ├─ Redis  job_state:{job_id}          1 hour   running scoreboard for one generation job
  ├─ Redis  conversation:{session_id} 24 hours  chat thread, last job, exec-repair history
  ├─ Redis  celery-as-broker/backend    Celery task metadata (execution_status)
  ├─ Redis  job_charge:{job_id}        unused today (legacy settlement lock)
  ├─ stdout logs                       pandas_generation_attempt, pandas_attempt_outcome, …
  └─ Supabase ledger                   durable credit receipts (event_type=llm_call)

    GET /api/v1/get_task_status/{task_id} is the read API for job telemetry. Redis is authoritative; Celery AsyncResult is a fallback when Redis has no row (unusual for current jobs).

    Celery worker

    The worker is the main telemetry producer. Admission queues code_generator_task with a stable task_id that is the job_id. That task builds a Plan and dispatches run_stage_task once per Stage (and again on sandbox retry). Legacy v1 still uses planner_task → compiler_task → routing_task.

    Worker settings that affect observability (app/core/celery_app.py):

    Setting Value Effect
    task_track_started true GET /get_task_status can show Celery STARTED, not only PENDING / SUCCESS / FAILURE
    task_acks_late true A killed worker redelivers the task; job_state may already contain partial token/billing totals
    worker_prefetch_multiplier 1 One job at a time per worker process

    The status poll payload includes both:

    • execution_status — Celery (PENDING, STARTED, SUCCESS, FAILURE, …)
    • dag_status — product pipeline status from Redis (generating_code, success, …)

    Job lifecycle (job_state:{job_id})

    Created by queue_generation_task before apply_async. Ownership (client_id) is set once and cannot be overwritten by later worker updates. Cancellation wins over late status writes.

    Initial fields:

    Field Meaning
    status queued
    client_id API-key client that owns the job
    cancel_requested / cancel_requested_at / cancelled_at / cancelled_by Cooperative cancel
    created_at UTC ISO timestamp
    billing.model_id Catalog model id from the request (scoreboard seed; totals accumulate later)

    Every Stage then merges through update_job_state (app/core/job_state.py). Token maps are additive. Result maps overwrite keys except the protected ownership/cancel fields.

    Pipeline status values

    Pandas Plan (app/generation/plans/artifact_graph.py):

    Stage status while running status when the stage succeeds
    (queued, plan persisted) queued —
    generate_pandas generating_code code_generated
    compile_dag compiling_from_code compiled
    format_visualization formatting_visualization visualization_formatted
    validate_visualization validating_visualization visualization_validated
    validate_dag validating validated
    finalize_plan finalizing success (written by finalize_success)

    Cross-cutting statuses: retrying (sandbox or compiler retry queued), failed, cancelled. Optional-stage failure does not fail the job: the worker records the slot as failed and continues.

    Legacy v1 (planner_task chain): planning, planning_completed, compiling, compiled, validating, retrying, success, failed.

    Plan and artifact scoreboard

    Persisted on every _persist_plan_fields write:

    Field Meaning
    capability_id Always data_analysis today
    plan_id data_analysis/pandas
    plan Full Plan dict (stage ids, options, status labels)
    current_stage / stage_index Stage currently running or just finished
    compile_dag / include_visualization Request options that shaped the Plan
    artifacts[] Typed envelope written at success (kind, schema_version, storage_key, payload)
    artifact_slots[] Canvas slots: { kind, status, reason? }
    requested_artifact_kinds Kinds the request asked for

    Slot status values (build_artifact_slots): not_requested, pending, ready, failed, skipped.

    Retry and attempt counters

    Field Meaning
    pandas_retries Sandbox retries used in this job (sandbox_max - pandas_sandbox_retries_left at accept/reject time)
    pandas_sandbox_retries_left Remaining in-cloud generate_pandas retries (reset on each runtime-repair job)
    pandas_retries_left Remaining local-exec repair jobs (POST /conversation/result)
    pandas_attempts_used LLM generate/repair calls consumed across the whole chain (sandbox + runtime repair jobs)
    pandas_total_max_attempts Hard ceiling (generation.yaml, default 9)
    generation_attempts Bounded list of per-call diagnostics (see below)
    last_pandas_error Last sandbox/preflight/runtime error string
    last_failed_code Last rejected pandas candidate (not executable)
    compiler_retries Compiler/viz retries used (max_retries - retries_left)
    last_compiler_error Last DAG compile/validate error
    errors[] Current failure list (cleared on success)
    pandas_code / graph / visualization_spec Latest accepted artifacts. Rejected pandas candidates are stored as last_failed_code, not as executable pandas_code.

    Runtime repair copies pandas_attempts_used, generation_attempts, and error history from the previous job into the new job’s worker config so the chain ceiling is not reset. It resets pandas_sandbox_retries_left to pandas_sandbox_max_retries so a depleted sandbox budget cannot block in-job retries on the repair.

    Token and latency totals

    Every Stage that returns StageResult.tokens feeds update_job_state(..., tokens=...). The merge is cumulative for the job:

    Field Source Notes
    input_tokens tokens.input_tokens or prompt_tokens Sum across all billed LLM calls in this job
    output_tokens tokens.output_tokens or completion_tokens Visible completion tokens as reported by the provider
    reasoning_tokens output_token_details.reasoning Sum; 0 when the model does not report hidden reasoning
    llm_times[] tokens.llm_time when > 0 Per-call wall time in seconds (pandas generate currently sets this)
    total_llm_time sum of those Same unit

    Compiler, visualization formatter, planner, and semantic-agent-on-worker paths pass LangChain usage_metadata through as tokens. They usually do not set llm_time, so llm_times is pandas-generation-centric.

    HTTP-side LLM calls (intent classifier, semantic analysis, answer synthesizer) are billed but do not land in this job_state. Poll get_task_status for worker usage only. Conversation classifier/semantic charges appear only on the Supabase ledger (no job_id).

    Per-attempt diagnostics (generation_attempts)

    This is the structured contract between CodeGeneratorService.generate and the rest of the stack. One object per pandas LLM call, kept to the last pandas_total_max_attempts entries.

    Emitted twice as JSON logs, then stored on the job:

    1. pandas_generation_attempt — immediately after the LLM returns, before preflight (code_generator.py).
    2. pandas_attempt_outcome — after accept/reject, with outcome fields (data_analysis.py).

    Fields written at invoke time

    Field Meaning
    attempt_index 0-based index in the chain (pandas_attempts_used before this call)
    retry_source initial (first pass), sandbox (in-job preflight retry), runtime (local exec repair job)
    trigger_category Failure category that caused this call (none on first pass)
    policy_profile catalog on first pass; otherwise a pandas_repair_profiles key (syntax, length, runtime, repeated_failure, …)
    reasoning_effort Effective reasoning effort (none / low / medium / …)
    max_tokens Completion cap used for this call
    finish_reason Provider finish reason (stop, length, …) from response_metadata
    input_tokens This call only
    output_tokens This call only
    reasoning_tokens Hidden reasoning tokens for this call
    latency_seconds Wall time around the invoke
    code_length Characters of extracted code (0 if empty)

    Fields added after preflight

    Field Meaning
    outcome accepted or rejected
    failure_category null when accepted; otherwise length, empty_output, syntax, invalid_unicode, sandbox_policy, runtime, …
    error_summary First error string, truncated to 300 characters (rejected only)
    error_signature Stable {category}:{normalized message} for repeated-failure detection

    Categories are defined in app/generation/llm_call_policy.py. repeated_failure is a policy profile, not an outcome category: if the same signature appears twice in history, the next repair uses the repeated_failure profile.

    A truncated completion (finish_reason=length) records failure_category=length on the attempt, but the history entry keeps the previous actionable error and sets truncated=true. The next repair prompt still targets that error; call parameters may use the length profile (no reasoning, higher max_tokens) so hidden reasoning cannot replace the original defect as the repair target.

    Sandbox rejects that still have budget set job status to retrying and re-queue run_stage_task for generate_pandas. Exhaustion sets failed and zeroes pandas_sandbox_retries_left.

    Job billing scoreboard

    While a stage runs, run_stage_task wraps the Stage in billing_scope(client_id, job_id=job_id). Every invoke_llm / invoke_llm_chain then:

    1. Charges the portal balance (llm_call ledger row with this job_id).
    2. Increments Redis billing on the same job.
    billing field Meaning
    model_id Seeded at queue time (request model)
    token_credits Sum of token-derived credits
    surplus_credits Sum of surplus
    charged_credits token_credits + surplus_credits
    llm_calls Number of billed invokes in this job
    surplus_rate Rate from the first charge

    This is a running scoreboard, not the source of truth for “may we charge again.” The ledger is. Failed and cancelled jobs keep charges for calls that already completed. Unlinked owner developer keys skip settlement; Redis totals may still increment if a charge dict is produced, but charge_client_balance_sync returns success without writing a receipt.

    job_charge:{job_id} helpers in job_state.py are unused. They are leftover from a single-settlement design.

    Celery result backend

    Each task return value is stored in Redis as the Celery result. Typical payloads:

    • code_generator_task: { job_id, capability_id, plan_id, stages }
    • run_stage_task: { status, next_stage, artifacts } or { status: retrying, … } or terminal { status, pandas_code, graph, … }

    The poll endpoint prefers Redis dag_status and artifacts. execution_status is the only Celery-native field routinely shown to clients.

    _celery_retries (self.request.retries) is passed into finalize_success as celery_retries. Finalize no longer retries charging; the argument is unused.

    Structured logs (worker stdout)

    Dev workers run at --loglevel=info. Useful lines:

    Logger / prefix When
    pandas_generation_attempt {json} After every pandas LLM call
    pandas_attempt_outcome {json} After accept or reject (includes outcome)
    Pandas code generation returned empty content (finish_reason=…, reasoning_preview=…) Empty extract; warning
    Error updating job status: … Redis write failed inside _update_job_status (printed, not logged)

    Grep worker logs for pandas_generation_attempt or pandas_attempt_outcome to reconstruct a job without polling.

    Cloud API process

    The API process does not run Stages. It admits work, charges HTTP-side LLM calls, and exposes telemetry.

    Health (GET /health)

    runtime_health() pings Redis and celery inspect ping (1 s timeout), then adds Supabase config:

    {
  "status": "ok" | "degraded",
  "services": {
    "redis": { "ok": true },
    "celery": { "ok": true, "workers": ["celery@host"] },
    "supabase": { "ok": true, "host": "….supabase.co" }
  }
}

    Generation endpoints return 503 when Redis or a worker is down (ensure_generation_runtime). This is liveness, not per-job telemetry.

    Intent classification

    IntentClassifierService logs:

    Intent classified: {intent} (confidence=…, capability=…, plan=…)

    Conversation may also log Escalating meta_question to data_query (requires file computation).

    These calls run inside billing_scope(client_id) without job_id. Credits hit the ledger; they never appear on get_task_status.

    Semantic analysis

    POST /api/v1/analyze_query (and the conversation graph’s analysis node) accumulate n_in_tokens_semantic / n_out_tokens_semantic on the agent instance. The analyze endpoint returns them on the SemanticAnalysis object. Conversation does not copy those counters onto the session.

    Answer synthesis

    POST /api/v1/conversation/synthesize bills inside billing_scope(client_id) with no job id. Failures log Answer synthesis failed.

    Conversation session (conversation:{session_id})

    TTL 24 hours. Not a substitute for job_state; it is the chat control plane.

    Field Role in telemetry / repair
    session_id / client_id Ownership
    messages[] { role, content, intent, timestamp } plus exec_error on execution_result rows
    query_state Structured follow-up state
    current_dag / current_result Last local execution (result, exec_error)
    last_task_id Job to poll; also the job whose retry budgets are copied on repair
    last_generation_* Query, metadata, model, Plan options for repair without re-classifying
    pandas_error_history Cross-job error entries (errors, code, category, error_signature)

    GET /api/v1/conversation/{session_id} returns this document (minus internals the schema omits).

    Status poll (GET /api/v1/get_task_status/{task_id})

    Auth-only (readable after credits hit zero). Maps Redis job_state to the client payload: pipeline status, artifacts, retry counters, generation_attempts, usage totals, billing, plan/slot fields. See CLOUD_API_USAGE.md for a full example.

    Local engine and desktop

    The sidecar executes Artifacts. It does not call LLMs and does not write job_state.

    After POST /execute_pandas (and optional DAG execute), the desktop posts:

    POST /api/v1/conversation/result
{ session_id, pandas_code?, exec_error?, exec_result?, dag? }

    That is the only execution telemetry the control plane receives. On exec_error with remaining pandas_retries_left and chain attempts left, the API queues a new generation job (status: repairing) and copies attempt history forward with retry_source=runtime.

    The sidecar logs load/runtime errors to its own logger (safe_pandas_executor). Those lines never reach Cloud API logs unless the desktop forwards exec_error.

    Supabase credit ledger

    Durable billing telemetry. Table credit_balance_ledger_nolain_query (sql/003_account_balance.sql):

    Column Meaning
    user_id Portal user
    delta Negative for charges
    reason llm_call for model invokes
    job_id Set for worker calls; null for classifier / semantic / synthesize
    event_type llm_call, grant, settlement (unused), adjustment
    metadata Credit math for that call (model_id, model_cost_usd, token_credits, surplus_*, charged_credits)
    created_at When the receipt was written

    Sum delta where job_id = … to reconstruct worker cost. HTTP-side calls have no job id, so they cannot be joined to a generation job except by time and user.

    What is not collected

    Absent Consequence
    Trace / span IDs Cannot stitch classifier → worker → sidecar in one trace
    Per-stage latency except pandas llm_time Compiler/viz duration is not in llm_times
    Prompt / completion text in job_state Only code_length, error_summary, and artifacts
    Model name per attempt Scoreboard has request model_id; attempts do not repeat it
    Sidecar CPU, row counts, exec wall time Only exec_error / exec_result preview
    Celery Flower / task events No event monitor
    Prometheus / OTLP No metrics scrape endpoint
    job_charge:* Helpers exist; nothing calls them

    How to read a job

    1. Live: GET /api/v1/get_task_status/{task_id} until dag_status is success, failed, or cancelled. Inspect generation_attempts, billing, token totals, and artifact_slots.
    2. Worker logs: grep pandas_generation_attempt and pandas_attempt_outcome (JSON after the prefix).
    3. Redis: GET job_state:{job_id} (TTL 1 hour). Conversation repair context: GET conversation:{session_id}.
    4. Money: ledger rows with that job_id. Conversation overhead is ledger rows with job_id null around the same time.
    5. Health: GET /health if jobs never leave queued.
