    System philosophy

    This document describes what the system is, how work moves through it, which rules are load-bearing, and which decisions steer behavior (cost, quality, trust). It uses layers and product language, not services, endpoints, or config file names.

    For components, contracts, and where policies are configured, see SYSTEM_ARCHITECUTRE.md.
    For the desktop chat loop in operational detail, see CONVERSATION_WORKFLOW.md.

    The core bet

    Nolain is a local computation product with a remote reasoning service, not a cloud analytics warehouse.

    The user’s file stays on the machine that already has it. The remote side sees a sketch of the data (schema, types, summaries, samples) and returns artifacts — executable analysis, an optional computation graph, an optional chart contract — that the local engine can run. Results are true because they were computed against the real file, not because a model claimed them.

    That split is the product. The workflow below is how the split is kept reliable, cheap enough, and hard to misuse.

    Layers

    Four layers, from closest to the user to farthest from the data.

    Local layer          data, metadata, execution
Dialogue layer       whether this turn should generate anything
Synthesis layer      admitted generation → typed artifacts
Settlement layer     identity, model choice, cost of reasoning

    Each layer has a job it must do, and a class of decisions it must refuse. The control plane is dialogue + synthesis + settlement (reason, admit, charge). The data plane is local (own the file, compute, report). Metadata is the only interface between them.

    Local layer

    Responsibility. Own the file. Derive the sketch. Execute artifacts. Show results. Report what happened.

    This is the only place that may touch the full dataset. It is also the only place whose output counts as an answer: a number, a table, a chart from real rows.

    What it refuses. It does not invent analysis. It does not call models. It does not decide product scope. If synthesis returns nothing executable, this layer has nothing to run.

    Strength. Privacy is structural, not a policy checkbox. Execution latency is local. The engine can grow without teaching the remote side about the user’s rows.

    Assumption. The sketch is a good enough surrogate for the file that generated artifacts will usually run. The user (and the desktop) can be trusted to execute what comes back and to report success or failure honestly.

    Tradeoff. Generation quality is capped by the sketch. Rare values and file-specific quirks that never appear in samples will surprise the model. Sending the file would raise hit rate and destroy the privacy bet.

    Dialogue layer

    Responsibility. Treat each user turn as a conversation decision, not as a generation request. Classify intent. Answer from the sketch when that is enough. Refuse what is off-topic, harmful, underspecified, or outside enabled products. Ask for clarification when the question is ambiguous. Only then admit generation.

    This layer is a gate. Most turns should never reach synthesis. That is a cost decision and a safety decision.

    What it refuses. It does not pick pipelines or optional artifacts. Intent is not a product. “The user wants a chart” is not “invent a visualization product.” Optional outputs are the user’s (and the desktop’s) choices.

    Strength. The conversation can be useful without a generation job: column lists, explanations of a prior result, a clear “we don’t do that yet.” New products can appear in the catalog without turning the gate into a planner.

    Assumption. A cheap classification, plus a deterministic override for clearly out-of-scope wording, is enough to keep generation rare and on-product. Fail-open (treat a broken classifier as a data question) is better than silently dropping real questions.

    Tradeoff. Fail-open spends money and can admit work that should have been refused. Clarification adds a turn — and a charge — before any artifact exists.

    Synthesis layer

    Responsibility. Once generation is admitted, produce typed artifacts under a registered Capability, through a Plan. Policy rebuilds the Plan. The model fills in artifacts; it does not design the machine that produces them.

    • A Capability is a product (“descriptive analysis of one file”).
    • A Plan is an engine for that product (one implemented engine today; others may be catalogued and still refused).
    • Stages consume and produce artifacts.
    • Optional artifacts (graph, chart) are request options on a Plan, not extra products.

    What it refuses. The model does not select Capabilities, Plans, or the shape of the pipeline. Unknown or unimplemented Plans are rejected. A dashboard is an artifact, not a Plan. Understanding the question (semantic analysis) happens before admission; it is not itself a Capability.

    Strength. One Plan can grow optional outputs without a combinatorial explosion of products. Deterministic checks sit next to generative steps so retries have something other than “try again” to push against.

    Assumption. Executable analysis is the primary artifact; the graph and the chart are projections of that analysis (and the question). Local execution plus a bounded repair loop will catch a useful fraction of mistakes without reopening the dialogue gate.

    Tradeoff. Code-first means the graph can drift from what actually ran, and a chart contract can disagree with both. Repair re-generates from the failure, not from a deeper reading of the question.

    Settlement layer

    Responsibility. Know who is calling. Offer a catalog of models. Charge for reasoning work as it happens (each model call), not for “a query” as a lump. Keep the control plane from doing work it cannot bill or should not admit.

    What it refuses. This layer does not execute data. It does not decide whether a question is in scope. A caller with no portal account (except a dedicated developer credential) does not get a path through. An empty credit balance does not get another job.

    Strength. One model gateway keeps the product from growing a provider-shaped codebase. Charging per call matches actual cost: a job with a graph and a chart is several calls, not one.

    Assumption. Immediate settlement on each call is acceptable even when a later step fails. Users will tolerate paying for the gate, for clarification, and for failed compiles because those were real model calls.

    Tradeoff. Price follows token usage, so the same question costs different amounts on different models and on retry-heavy paths. Conversation memory that lives in a short-lived store will vanish.

    How work flows

    The system is a loop between the data plane and the control plane. The file never crosses that boundary. Artifacts and a sketch do.

    Local:  load file → sketch
   → Settlement: who is this, may they spend?
   → Dialogue: open a session on that sketch
   → Dialogue: each turn → refuse | answer | clarify | admit
        ↳ if admitted: Policy rebuilds a Plan
        ↳ Synthesis: artifacts (with internal checks and bounded retries)
   → Local: execute artifacts on the file
   → Dialogue: store the outcome (follow-ups, explanations)
        ↳ if execution failed and repair budget remains:
             Synthesis again (no new classification) → Local again
   → optional: Settlement-charged framing of the result into narrative

    1. Presence — the file becomes a sketch

    The user loads a table on the desktop. The local layer reads it and produces a sketch: column names, types, summaries, sample values. That sketch is what every later layer is allowed to see.

    Restriction. The full file does not leave the machine. If the sketch is wrong or thin, every downstream step inherits that error.

    2. Identity — settlement before work

    Before any conversation turn or generation, settlement asks: is this a known caller, and may they spend?

    Caller Admission Charged for model work
    Portal-linked account with remaining credits Yes Yes
    Portal-linked account with empty balance No —
    Unlinked non-developer credential No —
    Dedicated unlinked developer credential Yes No

    Restriction. Queueing work is not itself a charge. Every model call that does run is charged as soon as it completes, including calls that later look wasted (a compile that fails, a gate that then refuses). Local execution is never a cloud charge.

    3. Session — dialogue binds a sketch to a thread

    Dialogue opens a session: a short-lived memory of messages, the current sketch, and (later) the last result. No model call is required to open it.

    Restriction. The session is not a durable account object. It expires. It is not a strong proof of ownership. Follow-ups and explanations are only as good as what that memory still holds.

    4. A turn — dialogue decides the branch

    The user asks a question. The desktop sends the message, the current sketch, and the user’s choices about optional artifacts (whether they want a computation graph, whether they want a chart). Those choices belong to the local layer / the user, not to the model.

    Dialogue classifies the turn once, then branches. Classification is a model call (settlement charges it). A wording-based safety override can still force “out of product” even if classification wanted to generate.

    Kind of turn What happens Reaches synthesis?
    Off-topic, harmful, or too vague A short refusal or a prompt for a better question No
    Answerable from the sketch alone (columns, row count, types) Answer from metadata; no generation No
    Explain a prior result or method Grounded text from stored outcome No
    Data-related, but no enabled Capability can serve it Named refusal (forecasting, inference, optimization, anomaly detection, and anything else the catalog cannot do) No
    Ambiguous data question Ask for clarification; wait for the next turn Not yet
    Clear data question Semantic reading of the question, then admission Yes, if still clear
    “That result looks wrong” Treat as a new generation with the prior question plus the feedback Yes

    Restriction. A user message is not a generation request until this layer says so. The classifier may suggest a Capability and a Plan for generation turns. It must not choose optional artifacts, and it must not invent a product. Policy, not the prompt, is authoritative.

    Fail-open. If classification fails to parse, dialogue treats the turn as a data question and continues toward admission. That spends money in order not to drop a real question.

    Clarification shortcut. Once the user has answered a clarification, the next send may skip classification and semantic reading and go straight to admission. The question’s meaning is treated as settled.

    5. Admission — policy, not the model, builds the Plan

    For generation turns, a second look at the question (semantic analysis) may still stop the flow: if terms are ambiguous, dialogue asks; if that reading fails, it answers in text and does not generate.

    If the question is clear, policy admits:

    1. The Capability must be registered and enabled. Unknown ids fall back to the one enabled product (descriptive analysis of one file).
    2. The Plan must be a known engine for that product. An unimplemented engine is rejected, not approximated.
    3. Optional artifacts come from the client’s toggles, not from the classifier.
    4. The server rebuilds the Plan. The model never selects the pipeline.

    Restriction. There is one enabled Capability today. Everything else is out of scope until a new Capability is registered and enabled. A chart is not a different product; it is an optional artifact on the same Plan.

    6. Synthesis — artifacts, checks, bounded retries

    Admitted work produces artifacts under the Plan:

    1. Primary artifact: executable analysis (code) from the question and the sketch.
    2. Optional graph: a computation-graph view derived from that code, if the user asked for it.
    3. Optional chart contract: a renderer-neutral spec, if the user asked for it.

    After each generative step, a deterministic check may reject the artifact (static sandbox on code; structural validation of the graph; contract validation of the chart). Rejection spends a retry budget and re-runs the generative step that produced the bad artifact. Two budgets exist and do not borrow from each other:

    • a budget for producing executable analysis (also shared with local-exec repair, below);
    • a budget for graph/chart compilation and validation.

    Restriction. Synthesis does not execute the user’s file. It may only inspect the sketch and the artifacts it has already produced. Code that fails the static sandbox never ships. When analysis is regenerated, derived artifacts (graph, chart) are invalidated and must be produced again if still requested.

    Settlement. Each model call inside this work is charged immediately. A failed compile still costs. Local execution, when it happens, does not.

    7. Execution — only the local layer may compute

    The desktop receives artifacts and runs them against the real file. That is the first moment the analysis meets the data.

    Restriction. A successful job on the control plane is not an answer. The local result is. The control plane is not charged for this step.

    8. Report and repair — execution feedback without reopening the gate

    After every local run, success or failure, the desktop tells dialogue what happened. A successful result is stored for later explanation and follow-up.

    If execution failed, and the analysis-retry budget still has remaining attempts, dialogue does not classify again. It sends the failed artifact and the error back to synthesis (a repair). The desktop waits, executes the new artifacts, and reports again, until the run succeeds or the budget is exhausted.

    Kind of correction When Re-enters dialogue classification?
    Internal synthesis retry Artifact rejected by a static check before it ships No
    Runtime repair Artifact passed checks but failed on the real file No

    Restriction. Repair cannot change what the question meant. It cannot spend more than the remaining budget. It cannot turn a data question into a different Capability. Graph/chart retries are a separate budget and are not spent here.

    9. Framing — narrative is optional and after the fact

    Once a result exists, the desktop may ask for a narrative wrapping. That is another model call (charged). It must not replace the executed result. If framing fails, the user still has the numbers.

    Two entry points

    The loop above is the conversation path (the desktop product).

    There is a direct generation path: skip session and dialogue, admit a Capability from the request, run synthesis, return artifacts. That path does not classify, does not clarify, and does not run the local repair loop. It is the same product with the gate and the memory stripped off.

    Restriction. Those two paths must not silently become two products. Direct generation is the same Capability and the same artifacts; it is honest about omitting the gate.

    Steering policies

    The philosophy is not only layers and workflow. It is also explicit decisions that aim the system: what to optimize on the happy path, what to spend when something fails, and what must never be delegated to the model.

    These decisions live in configuration and in code. The important part is the direction, not the knob name. Changing a steering policy is a product bet — “we now value X over Y” — not a cosmetic tweak.

    Emit fast, keep repairs executable

    Decision. First-pass artifact generation uses minimal model reasoning. Surgical repairs — syntax, invalid unicode, sandbox policy, and runtime column/name fixes — also emit with reasoning disabled. Hidden reasoning is not spent on those paths because reasoning tokens share the completion budget and can starve the visible program.

    Why. First pass is emission: turn a clear question and a sketch into executable analysis. Extra “thinking” mostly adds latency and cost without improving code that must pass deterministic checks anyway. A typo, a zero-width space, or a bad column name is still emission of a short corrected program, not open-ended diagnosis. When a repair call hits the token limit, the original actionable error is kept as the next prompt target; truncation is call metadata.

    Direction. The system prefers cheap, direct generation, and pays for longer visible completions on repair rather than hidden reasoning. Deterministic fixes (strip illegal format characters, localize runtime line numbers) run before any model retry.

    Separate retry budgets

    Decision. Retries are not one pool. Analysis has distinct budgets for (a) in-cloud rejection before anything ships, (b) local execution failure reported back, and (c) graph/chart compile and validation. Pandas calls also share a chain-wide ceiling so nested repair jobs cannot multiply total model calls.

    Why. A compile loop should not consume the user’s allowance for “the code was right but my file surprised you.” A sandbox reject should not exhaust the budget for real execution feedback. Each failure mode has a different fix; lumping budgets would either starve repairs or over-spend on cheap rejects.

    Direction. Failures are bounded and typed. Source budgets preserve the meaning of each retry, while the chain ceiling bounds total cost.

    Checks before ship, execution only local

    Decision. Executable analysis is inspected on the control plane with static policy (no running the user’s data in the cloud). Graph and chart contracts get deterministic validation after generative steps. Only the local layer runs against the file.

    Why. The privacy bet forbids cloud execution on full data. Static rejection catches a large class of unsafe or unusable code early. Validation gives retries a concrete error, not “try again.” Local execution is the ground truth the sketch could not provide.

    Direction. Trust is staged: sketch → generated artifact → checked artifact → executed result. Each stage can send work backward; none skips straight to “believe the model.”

    Regenerate downstream when upstream changes

    Decision. When executable analysis is regenerated (repair or sandbox retry), derived artifacts — graph, chart — are invalidated and rebuilt if still requested.

    Why. Derived views are projections of the analysis. Keeping an old graph attached to new code would lie to the user about what ran.

    Direction. One primary artifact anchors truth; everything else follows it or disappears.

    Model catalog vs repair profile

    Decision. The model catalog sets defaults for which models exist, default reasoning per model, and routing preferences. Pandas repair selects a profile from the normalized failure category and retry index. Syntax, Unicode, sandbox-policy, and first runtime repairs emit compact code with reasoning disabled. A truncated repair keeps the original error as the prompt target and may raise max_tokens without turning reasoning back on.

    Why. Catalog defaults optimize the common case across all call sites (classifier, semantic reading, compile, chart format). Repair is a different job with different economics; it should not inherit “fast emitter” settings.

    Direction. Defaults are for throughput; evidence from the actual failure chooses the recovery budget.

    Charge the call, not the question

    Decision. Every model invocation settles immediately when it completes. Queueing synthesis is not a charge. Local execution is never a charge. A margin (surplus) is applied on top of raw token cost.

    Why. Vendor cost is per call. Hiding failed compiles or gate calls inside a flat “query price” would misalign product and infrastructure. Surplus funds variance (retries, pricing drift) without pretending one successful path defines the price of reasoning.

    Direction. Users pay for reasoning work that actually happened. The product is honest that a “simple question” can be several calls.

    Gate: fail-open, then narrow

    Decision. If intent classification breaks, treat the turn as a data question and continue toward admission. A separate wording-based safety layer can still refuse forecasting, inference, optimization, and anomaly detection. The classifier must not set optional artifacts.

    Why. Fail-open favors not losing real questions over not spending on junk. The safety layer catches a small set of high-risk asks that should never reach synthesis even when classification misfires. Optional artifacts stay with the user/desktop so the gate cannot silently turn on expensive outputs.

    Direction. The conversation gate is permissive on machinery failure, strict on product boundary, silent on user toggles.

    Admission is server-side

    Decision. Models may suggest a Capability and Plan; policy rebuilds the Plan from the registry and client toggles. Only enabled Capabilities admit. Unknown Plans reject; unimplemented Plans reject.

    Why. Prompts drift; registries do not. Letting the model pick pipelines would make every new product a prompt edit instead of a registration.

    Direction. Extensibility through registration, not through chat creativity.

    Reasoning-capable models still emit on the happy path

    Decision. Even when the chosen model supports extended reasoning, code and JSON emitters default to no extra reasoning effort on first pass and on surgical Pandas repairs. Heavier models in the catalog may use more reasoning for tasks that need it (e.g. explanation paths).

    Why. Reasoning tokens are expensive and invisible to the user until they fail. For structured output that will be validated anyway, thinking is often waste.

    Direction. Use the model’s strength for output quality and validation loops, not for open-ended cogitation on every turn.

    Where steering is configured

    Tunable steering (source retry budgets, chain attempt ceiling, category repair profiles, model defaults, credit formula) lives in policy files loaded at startup. Structural rules (admission, failure classification, sandbox, intent routing, charge timing) live in code. The architecture doc maps file to concern; this doc maps decision to intent.

    When you change a value, ask: which direction does this push? Examples:

    If you increase… You are saying…
    Repair reasoning effort Failures deserve more diagnosis; accept higher cost on the error path
    Sandbox retry budget Reject early, retry often, before the user ever runs code
    Exec-repair budget Local truth matters; keep trying after the sketch misled generation
    Compile/chart retry budget Derived artifacts must be structurally valid, not just plausible
    Default reasoning on emitters Willing to pay latency/cost on every first pass for possibly better code
    Surplus rate Pricing should carry more buffer above vendor cost
    Fail-open → fail-closed Prefer refusing ambiguous turns over spending on possible junk

    Policies and restrictions

    These are the rules the workflow is not allowed to “work around.” Changing them is a philosophy change.

    Data

    • The file stays local. The sketch is the only remote view of the data.
    • One loaded table is the unit of analysis.
    • Enabled product: descriptive work on that table (aggregations, comparisons, rankings, trends, quality checks, reshape, optional charts).
    • Not enabled until a Capability says so: forecasting, statistical inference, optimization, anomaly detection, and anything else the catalog does not name.

    Authority

    • Models propose; policy admits. Registries and client options are the source of truth.
    • Intent (conversation branch) is not a Capability (generation product). Mixing them would let a prompt invent a pipeline.
    • Optional artifacts are user/desktop toggles on one Plan, not new Plans and not classifier output.
    • Unimplemented Plans are rejected. Unknown Capabilities fall back to the enabled default; they are not invented.

    Generation

    • Generation is admitted, not assumed.
    • Semantic reading of the question is a gate, not a product.
    • Executable analysis is primary; graph and chart are derived and optional.
    • Static checks must pass before an artifact ships. Execution happens only locally.
    • Fail-open on classifier failure; wording-based safety may still refuse an admitted-looking data question.

    Repair and memory

    • Runtime repair is execution feedback, not a new conversation.
    • Dialogue memory is short-lived and weakly bound to the caller.
    • Cooperative cancellation may stop work between steps; model calls already completed stay charged.

    Settlement

    • Charge the reasoning, not the job. Each model call settles when it completes.
    • Empty balance: no further admitted work.
    • Local execution is free to the cloud.
    • Developer credentials that are not tied to a portal account skip settlement; every other caller does not.

    Cross-cutting rules

    Control plane vs data plane. The cloud may reason. Only the local layer may compute on the file. If the sketch is too thin, generation quality falls; if it is too thick (full rows, full files), the split collapses.

    Suggest, then decide. This is how the system stays extensible without letting a prompt invent a product.

    Artifacts are the contract. The desktop does not consume “a job succeeded.” It consumes executable analysis, a graph, a chart spec.

    The conversation may refuse. A useful product is allowed to say no, to explain, or to answer from the sketch.

    Strengths (as a whole)

    • Structural privacy. The file never has to be uploaded for the product to work.
    • Answers grounded in execution. The UI can show what ran, not only what was said.
    • A conversation that can refuse. Most turns never reach synthesis.
    • A small, explicit product surface. One Capability, one implemented Plan, optional artifacts.
    • Deterministic belts around generative steps. Checks give retries a target.
    • Cost aligned with work. Credits track model calls. Local execution is free.

    Assumptions (as a whole)

    • The sketch is representative enough, often enough.
    • A single executable-analysis engine is a sufficient lingua franca between control plane and data plane.
    • The desktop is a trusted partner: it executes, it reports, it owns optional-artifact toggles.
    • Bounded retries and a fail-open gate are preferable to silent refusal.
    • Users will accept paying for the gate and for failed steps because those were real model calls.

    Tradeoffs worth naming

    Choice What it buys What it costs
    Sketch only, never the file Privacy, simpler trust, local truth Missed quirks; generation can be locally wrong
    Intent gate before generation Cheap refusals; clearer product boundary Extra calls; fail-open can admit junk
    Classifier suggests, policy admits The model cannot invent pipelines Catalog and policy must stay the real source of truth
    Optional artifacts, not extra Plans One Plan, many outputs Options must be carried on every turn; easy to document wrong
    Analysis first, graph and chart derived Fast path to something executable Drift between code, graph, and spec
    Repair without re-classifying Fast correction on exec errors Repair cannot change the question’s meaning
    Charge every model call immediately Matches vendor cost; no “job-shaped” fiction Users pay for failed steps and for the gate itself
    Short-lived session memory Simple operations History is not a durable account object
    Single enabled Capability Honest “out of scope” Dialogue must keep saying no
    Direct generation beside conversation Same artifacts without a chat Two paths that can drift if they are not kept honest

    Room for improvement

    The current shape is a working compromise, not a finished architecture.

    The sketch is still a sketch. Better summaries, better samples, and honest signals about data quality would raise hit rate without moving the file.

    One Capability is both a strength and a ceiling. “Out of scope” is doing a lot of work. A second product will test whether intent, policy, and artifacts actually compose.

    A second engine is a promise. Until another Plan is implemented, “Plan = engine” is vocabulary, not a proven split.

    Code, graph, and chart can disagree. Treating the graph as a projection is convenient. Making it the executable source of truth would make the canvas trustworthy. That is not done.

    Dialogue is a good gate and a weak memory. Sessions expire, ownership is weakly bound, and follow-up quality depends on whatever was last stored.

    Fail-open and wording-based safety are temporary ethics. Admission should eventually fail closed on classifier failure. Out-of-scope should come from the Capability catalog, not from phrase lists.

    Settlement is call-shaped; the product is still question-shaped. Clearer receipts and budgets per question would make “pay for reasoning” feel like a product.

    The local layer is trusted more than it is isolated. Policy can constrain what ships; it cannot make local execution a full sandbox of an untrusted world.

    How to use this document

    When adding a feature or changing a configured value, ask:

    1. Which layer owns it?
    2. Which steering policy does it extend or contradict?

    Layer ownership:

    • If it touches the file or the result, it belongs in the local layer.
    • If it decides whether to generate, it belongs in dialogue.
    • If it produces something executable or viewable, it belongs in synthesis — not a new intent, and not a new Plan for a toggle.
    • If it is about who pays or which model runs, it belongs in settlement.

    If a change requires the control plane to see more of the file, the model to pick a pipeline, a new Plan for what is really an optional artifact, or a second entry path with different semantics, it is fighting this philosophy. That can still be the right call — but it should be named as a bet change, not as a small addition.

    If a change only adjusts a config value, state the direction (the table in Steering policies) so the team knows what tradeoff moved.
