    Shipping to production

    This chapter is for someone who needs a change to reach the live site. It answers what the release path is, why build and deploy are separate steps, and how to run them for this repository.

    Three product repositories and one infra repository share a single VPS. Building images and deploying the stack are separate on purpose: a green build does not restart production by itself. That keeps a broken image from going live because a push happened to succeed, and it lets you build OCR and Query independently, then cut over together.

    Infra setup (runners, keys, and the first-time VPS layout) belongs to the separate nolain-platform repository. This page documents the release flow after that infrastructure is available.

    The picture, as a sequence rather than a graph:

    1. A push to nolain-ocr (branch master) or nolain-query (branch main / platform) builds Docker images on a self-hosted runner and pushes them to GHCR (GitHub Container Registry).
    2. Nothing happens on the VPS yet.
    3. Someone (or a push to nolain-platform) runs Deploy platform to VPS. That runner pulls the images and runs docker compose pull && up -d on the machine that actually serves traffic.

    The rest of the chapter is what each component does, what you do after a code change, and what to check when the site is still old.

    Components

    1. nolain-ocr — Build and push to GHCR
    What it does On push to master, builds backend and frontend Docker images on the VPS runner, pushes them to GHCR tagged :master, :latest, and :<git-sha>. Frontend build bakes in VITE_* values from GitHub secrets.
    Admin action required? One-time: GitHub secrets for every VITE_* the frontend Dockerfile expects. Per change: push to master (or Actions → Run workflow).
    Maintenance? Update nolain-ocr GitHub secrets when a new VITE_* build arg is added to the frontend, or when Supabase/Google/Stripe public IDs change.

    2. nolain-query — Build and push to GHCR
    What it does On push to main / platform, builds cloud_api backend and nolainquery-website images on the Query self-hosted runner (~/actions-runner-query). Tags: :main or :platform, :latest, :<git-sha>. Website bakes in VITE_SUPABASE_* from secrets; VITE_CLOUD_API_URL=https://nolainquery.com.
    Admin action required? One-time: register third runner on VPS for nolain-query; set VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY secrets (same Supabase project as OCR). Per change: push branch → wait for build ✅ → run platform deploy.
    Maintenance? Grant nolain-platform GHCR read access to new Query packages (or extend GHCR_PAT). While testing Phase 2, platform compose uses :platform tags; switch to :main after merge.

    3. nolain-platform — Deploy platform to VPS
    What it does On push to platform / main, or manual trigger: pulls latest platform repo on the VPS, logs into GHCR, runs docker compose pull && up -d using docker-compose.prod.yml and /opt/nolain/.env. Restarts nginx, OCR, Query, redis, celery workers. Reloads nginx config after up.
    Admin action required? One-time: GHCR_PAT secret on nolain-platform (read packages). Platform repo cloned on VPS with deploy key (Step 1.4 in guide). After product code changes: trigger this manually — it does not run when OCR or Query builds finish.
    Maintenance? Rotate GHCR_PAT before expiry. Update /opt/nolain/.env when backend runtime env vars change. Add Query keys (DEEPSEEK_API_KEY, QUERY_*) once (Phase 2).

    4. Self-hosted GitHub Actions runners (×3)
    What it does Executes workflow jobs on the VPS. One runner per repo: nolain-ocr (builds), nolain-platform (deploy), nolain-query (builds). All need the vps label.
    Admin action required? One-time: install and register all three; keep systemd services running (actions-runner, actions-runner-platform, actions-runner-query). Query runner may run via ./run.sh until root installs svc.sh.
    Maintenance? Upgrade runner version occasionally. Restart service if jobs sit in Waiting for a runner… while the runner shows Idle.

    5. GHCR (GitHub Container Registry)
    What it does Stores built images. Platform compose references OCR :master and Query :platform (or :main after merge).
    Admin action required? None for day-to-day — build workflows push; deploy workflow pulls.
    Maintenance? Ensure nolain-platform has package read access for Query images (403 → refresh GHCR_PAT or grant package access).

    6. VPS runtime — Docker stack + /opt/nolain/.env
    What it does Runs production containers (8 services after Phase 2). Shared Supabase keys; OCR Stripe/Mistral keys; Query DEEPSEEK_API_KEY and QUERY_* quotas. Nginx routes nolainocr.com → OCR, nolainquery.com → Query (HTTP until SSL cert; see guide Step 2.3).
    Admin action required? Edit .env on the VPS when backend env vars change. Point DNS nolainquery.com → VPS IP; run certbot for HTTPS.
    Maintenance? Backup .env and certbot/. Add Supabase redirect URL for https://nolainquery.com/**.

    7. Domains

    Domain Routes to
    nolainocr.com OCR frontend + /api → OCR backend
    nolainquery.com Query website + /api → Query backend

    Query uses HTTP on port 80 until Let's Encrypt cert exists for nolainquery.com (DNS must point to VPS first).

    After you change code

    OCR (nolain-ocr)

    What changed What you do
    Backend or frontend app code 1. Push to master. 2. Wait for Build and push to GHCR ✅. 3. Deploy platform to VPS (manual). 4. Confirm nolainocr.com.
    New VITE_* Update OCR secrets → push → platform deploy.
    Backend env var Edit /opt/nolain/.env → platform deploy.

    Data Query (nolain-query)

    What changed What you do
    Backend or website code 1. Push to platform (or main). 2. Wait for Build and push to GHCR ✅. 3. Deploy platform to VPS (manual). 4. Confirm nolainquery.com.
    New VITE_* Update Query repo secrets → push → platform deploy.
    Backend env var (DEEPSEEK_API_KEY, quotas) Edit /opt/nolain/.env → platform deploy.

    Platform (nolain-platform)

    What changed What you do
    Nginx / compose / infra Push to platform — deploy runs automatically.

    Short version: product push → wait for build ✅ → manually run Deploy platform to VPS.

    When automation is broken

    1. Build failed — open failed Build and push to GHCR run; fix code or restart the repo's runner service on VPS.
    2. Build OK, site still old — you likely skipped platform deploy. Run Deploy platform to VPS manually.
    3. Deploy stuck / runner idle — restart platform runner; trigger a new workflow run.
    4. Query site 301 to OCR / wrong backend — nginx config not reloaded: docker compose … exec nginx nginx -s reload or redeploy platform.
    5. Deploy fails on GHCR 403 — refresh GHCR_PAT or grant Query package access to nolain-platform.
    6. Query containers fail health — check DEEPSEEK_API_KEY in /opt/nolain/.env.

    What is not wired yet

    • Product builds do not auto-trigger platform deploy.
    • Billing service (Phase 3) not on VPS yet.

    Quick checklist (Query release)

    • [ ] Push nolain-query → platform (or main)
    • [ ] Build and push to GHCR green (backend + website)
    • [ ] Deploy platform to VPS run (manual)
    • [ ] docker compose ps — 8 containers Up
    • [ ] curl -H 'Host: nolainquery.com' http://<VPS_IP>/health → JSON ok
    • [ ] After DNS: certbot for nolainquery.com → enable HTTPS nginx block

    Quick checklist (OCR release)

    • [ ] Push nolain-ocr → master
    • [ ] Build and push to GHCR green
    • [ ] Deploy platform to VPS run (manual)
    • [ ] docker compose ps — all containers Up
    • [ ] https://nolainocr.com loads
