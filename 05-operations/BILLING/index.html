    Billing — developer and operator guide

    User-facing pricing and examples: CREDITS.md.

    Credit formula

    token_credits = ceil(model_token_cost_usd × credits_per_dollar)
surplus_credits = ceil(token_credits × surplus_rate)     # default 1.0 (100%)
charged_credits = token_credits + surplus_credits      # 0 if token_credits is 0

    Policy: app/config/billing.yaml (env overrides: CREDITS_PER_DOLLAR, CREDIT_SURPLUS_RATE, BILLING_CONFIG).

    Setting Default Env override
    credits_per_dollar 1000 CREDITS_PER_DOLLAR
    surplus_rate 1.0 CREDIT_SURPLUS_RATE
    MONTHLY_PLAN_CREDITS["free"] 1000 —
    MONTHLY_PLAN_CREDITS["premium"] 50000 —

    Model token rates

    Primary source: OpenRouter GET /api/v1/models (pricing keyed by each catalog model's openrouter_model slug in llm_models.yaml).

    Fallback: billing.yaml → pricing.model_overrides (USD per 1M tokens).

    Set pricing.source: yaml to use overrides only (tests, offline).

    Implementation: app/core/openrouter_pricing.py, app/core/credit_pricing.py.

    Consumption

    Billable API keys must be portal-linked (clients_nolain_query.user_id set). Admission reads profiles_nolain_query.credit_balance and returns HTTP 402 when the balance is empty.

    Unlinked owner keys (developer keys from scripts/ensure-developer-key.sql, with tier = 'owner' and no user_id) skip credit admission and settlement. Linked owner keys follow the same rules as free/premium portal keys.

    Unlinked non-owner keys are rejected with 402 (no portal account).

    Charge timing: every LLM invoke inside an active billing_scope(client_id). Workers wrap stage execution; HTTP handlers wrap conversation, analyze_query, and synthesize.

    Credit charges use the atomic RPCs in sql/003_account_balance.sql. Existing databases that still have query_balance should apply sql/008_credit_rename.sql. Configure Stripe packages as a JSON map, for example {"price_basic":"1000","price_team":"10000"}. The webhook accepts only paid sessions whose price_id and declared credits match this map.

    Receipts: one job, many LLM charges

    Every time the product calls an LLM (code generation, DAG, chart, and so on), two things happen:

    1. OpenRouter runs the model. That costs us money.
    2. The app then subtracts credits from the user's account so they pay for that call.

    A typical pandas job with a chart and a DAG is several LLM calls, not one. Each call should take some credits.

    Two stores are involved:

    • User balance (credit_balance) — a number: how many credits the user has left.
    • Ledger (credit_balance_ledger_nolain_query) — the receipt book. Each charge adds a row: “minus 6 credits for job X”, then “minus 4 credits for the same job”, and so on.

    When a charge works, both update: the balance goes down, and a new receipt is added. The receipt stores the job id so you can later ask what that query cost by summing its rows.

    Receipts are tagged with event_type:

    Tag Meaning
    llm_call One LLM call was charged. A job may have many of these.
    grant Credits were added (plan or Stripe top-up).
    settlement Reserved. At most one row of this tag per job.

    The database still has a rule: at most one settlement receipt per job. That is unused today. It is kept for a future “one total row for the whole job” if we ever need it. Per-call charges use llm_call, which that rule does not cover, so a job can have many receipts.

    If a later LLM call in the same job were written as settlement, the database would reject it (HTTP 409). The job would skip that stage even though the model already ran. Conversation endpoints that omit job_id never hit this rule.

    Redis job billing totals are only a running scoreboard. They do not decide whether a second charge is allowed. The ledger does.

    Manual testing

    1. Grant credits: update profiles_nolain_query set credit_balance = 1000 ...
    2. Run a pandas-only job (compile_dag: false, include_visualization: false).
    3. Poll GET /api/v1/get_task_status/{job_id} until success.
    4. Expect billing.charged_credits reflecting all LLM calls in the job.
    5. Repeat with compile_dag: true — expect higher totals (more LLM calls + tokens).
    cd cloud_api && PYTHONPATH=. pytest -q

    Known limitations

    Admission requires a positive credit balance for portal-linked keys. Unlinked owner developer keys skip admission and settlement. Each LLM credit charge is atomic; if writing the receipt fails, the call fails rather than continuing as if it were unpaid.

    Change checklist

    1. Update CREDITS.md if user-visible pricing changes.
    2. Keep billing.yaml and plan grants in sync.
    3. Ensure every catalog model resolves rates (OpenRouter or yaml override).
    4. Route all LLM invokes through invoke_llm / invoke_llm_chain.
