    DAG Connection Validation Tests

    Unit tests for the DAG visualization panel’s connection rules. They exercise validateConnection from desktop_app/frontend/src/dagGraphUtils.ts — the same function DAGEditor calls via isValidConnection when a user draws an edge in React Flow.

    No browser or drag-and-drop is involved; tests build minimal node/edge graphs in memory and assert allow vs deny outcomes.

    Quick start

    cd desktop_app/connection_validation_tests
npm install
npm test

    Verbose per-case output:

    npm run test:verbose

    Watch mode during development:

    npm run test:watch

    What is covered

    File Purpose
    src/structural.test.ts Graph-shape rules: cycles, self-loops, invalid handles, double-connect, non-wirable params
    src/connectionMatrix.test.ts Scope-class × port matrix, peer-context binary inputs, index.indices param rules
    src/registryParity.test.ts Drift between OP_META (editor library) and dagGraphUtils port registry
    src/scopeProducers.ts Canonical fixture nodes per scope class + expectation oracle
    src/fixtures.ts Node/edge builders and tryConnect helper
    src/paramSchema.ts Connectable param widgets mirrored from DAGEditor.tsx
    src/registry.ts Op lists for matrix enumeration

    Scope fixture bank

    Each scope class has one minimal producer node whose inferred scope is verified at test startup:

    Class Producer Inferred scope
    global filter_extract (no condition) Global
    condition_a filter_extract + Country == 'UK' Condition:Country == 'UK'
    condition_b filter_extract + Year == 2024 Condition:Year == 2024
    grouped_month groupby_agg by Month Grouped:Month
    grouped_year groupby_agg by Year Grouped:Year
    scalar load_constant Scalar
    derived unique ← global column Derived
    mask_global gt on global + scalar Global (inherited)
    mask_condition_a gt on condition_a + scalar Condition:Country == 'UK'

    Duplicate producers (prod_cond_a_2, prod_mask_global_2) share scope with their twins but use different node ids. They are used in peer-context tests so the validator’s cycle check does not treat “same node wired to two ports” as a cycle.

    Matrix dimensions

    For every op in the graph-utils registry (~70 ops):

    1. Input ports (input-0, input-1, …) × 9 scope classes × optional peer on port 0 (for binary ops) → 963 input combinations
    2. Connectable param ports (param-agg_column, param-indices, param-groupby_columns) × 9 scope classes → 27 param combinations

    Scope alignment is only enforced on:

    • BINARY_ELEMENTWISE_OPS (arithmetic, comparisons, logical_and/logical_or, etc.)
    • sum_if / mean_if (values ↔ mask pairing)
    • groupby_agg.params.agg_column (reject already-grouped sources)
    • index.params.indices (mask scope must match wired values input, unless scalar)

    Unary ops accept any scope on their single input port (matching current validateConnection behavior).

    How to read test results

    All green

     ✓ src/registryParity.test.ts (3 tests)
 ✓ src/structural.test.ts (11 tests)
 ✓ src/connectionMatrix.test.ts (18 tests)

 Test Files  3 passed (3)
      Tests  32 passed (32)

    The panel’s connection validator matches the documented rules for every enumerated port × scope combination.

    Matrix failure (EXPECTED ALLOW / EXPECTED DENY)

    The matrix test batches failures and prints up to 20 lines, e.g.:

    EXPECTED DENY: add:input-1<-condition_b — connection was accepted (scope Condition:Year == 2024)

    Read as: connecting producer condition_b to add port input-1 should be rejected (peer would be condition_a in peer-context tests; in the base matrix peers are empty so only elementwise self-alignment applies). A failure means validateConnection is too permissive or the oracle is wrong.

    EXPECTED ALLOW: groupby_agg:param-agg_column<-global — got "Cannot aggregate…"

    Means a legal connection was blocked — validator too strict or fixture scope wrong.

    Scope mismatch wording

    Denied scope cases should return an error containing Scope mismatch. If you see a different message, structural validation may be firing first (cycle, invalid port, etc.).

    Vacuous rules warning

    Scope-checked ops need both allow and deny cases: add (allowed=9, denied=0)

    The test suite requires every scope-checked op to have at least one allowed and one denied case in the matrix. Zero denied cases means the fixture bank does not exercise that op’s restrictions.

    Registry parity

    expected [ 'count_if', … ] to deeply equal [ 'count_if', 'new_op', … ]

    A new op was added to dagGraphUtils but not to the editor’s OP_META, or vice versa. Update src/registry.ts and either add the op to the editor library or document it as utils-only.

    Cycle detection note

    The structural cycle test wires n1 → n2 → n3 and then attempts n1 → n3 (a shortcut). The validator walks existing upstream edges from the target; if the new source is already an ancestor of the target, the connection is rejected. This matches wouldCreateCycle in dagGraphUtils.ts.

    Intentional limits

    • Does not test validateNodeParams (column names, Zod literals, condition syntax).
    • Does not test React Flow UI rendering or drag gestures.
    • Does not export OPERATION_CONTRACTS from Python yet; expectations are encoded in scopeProducers.ts to mirror validateConnection + known backend rules.
    • Derived + Derived connections are currently allowed by the frontend if both share the Derived label — a known simplification; the matrix documents current behavior rather than ideal backend semantics.

    Adding a new operation

    1. Add port labels to dagGraphUtils.ts (INPUT_PORT_LABELS, op class sets).
    2. Add connectable param widgets to DAGEditor.tsx PARAM_SCHEMA and src/paramSchema.ts.
    3. Add the op to src/registry.ts (OP_META_OPS if in the editor).
    4. Extend expectedInputAllowed / expectedParamAllowed in scopeProducers.ts if the op has non-default scope rules.
    5. Run npm test — matrix size grows automatically for new ports.
